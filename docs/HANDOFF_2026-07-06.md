## 2. システム構成（3段パイプライン）
1. **①計算骨格生成**: `Blueprint`（問題の型）＋`Atom`（Noun=図形/数, Verb=操作、SymPyで計算）が `MiddleRepresentation`(MR) を作る。
2. **②LLM翻訳**: `LLMTranslator`（Gemini `gemini-flash-lite-latest`）が MR を自然言語の問題文・解説へ翻訳。
3. **③図レンダリング**: `visual_dsl` を SVG 化。
- `master_data/mapping.json`（184レッスン）が各レッスンに Blueprint・`difficulty_levels`・`required_tags` 等を紐付ける中心データ。
- エンドポイント: `/problems/inspect`（POST, **LLM翻訳前の生MRを返す＝LLMフリー**）、`/problems/generate`（①②③通した最終問題＝実LLM）。
- Python 実行は必ず `.venv/bin/python`（system python に sympy 無し）。テスト: `SKIP_LLM_IN_TESTS=true .venv/bin/pytest tests/ -q`。

## 3. 伸び悩みの診断（Opusによる設計レビュー）

1. **計算骨格ファーストを全形式に強制**: SymPy数値骨格→LLM翻訳は `calculation` には最適（SymPyが正しさを保証＝moat）。

## 4. 中核戦略（ユーザー制約を満たす設計）

- **症状ごとのBlueprint追加で握り潰さない**。form/difficultyは構造で直す。

### 8.1 ペアリング設計（2026-07-06 検証で確定・重要）
**誤: GTに記録された `seed` を product に食わせる → NG。** 記録される `mr.seed` は**リトライ後の per-attempt seed**（`base_seed + attempt`）であり、`DiversityRotation`/atom棄却サンプリングがリトライ間で状態を持つため、その値を base_seed として注入しても run 全体は再現しない（実測で visual g1_l30 の3件が答え不一致になった）。
**正: 両スクリプトが同一の決定論 base_seed をキーごとに注入する。** `/inspect`・`/generate` はフレッシュな dedup/diversity を毎回構築するので、base_seed 固定なら run() 全体が純関数として同一MRを返す。パイロット5レッスン×3レベル=15キーで **15/15 完全一致（visual含む）を実測で確認済み**。
- 決定論 base_seed の算出は**共有ヘルパ**に置く（両スクリプトが同じ値を出すこと）。実測に使った式: `zlib.adler32(key.encode()) % 1_000_000 + 1`（key = `{lesson}_{form}_{level_label}` など）。この式を正とする。
- `build_ground_truth_corpus.py` は現状 seed 未注入。**pinned seed を注入して再生成**し、採用 base_seed を `_pinned_seed` として JSON に記録する（product 側が読める／再算出できるように）。
- product 生成用 runner は**フレッシュに構築**（/inspect と同様、dedup/diversity の永続状態を持ち込まない）。本番 `/generate` の共有 runner や PrefetchCache は跨ぎ状態があるため、コーパス用途では都度 new する（build_product 内で BlueprintRunner を直接構築 or /inspect と同経路で MR を得てから翻訳）。

## 10. 原則・落とし穴（厳守）
- 評価ループにLLMを入れない。ground truth とゲートは常にLLMフリー。product は稀に生成・凍結。
- SymPyの答えは不変（moat）。ゲートは検査するが変更しない。
- ゲートは純関数＋データ外出し。個別レッスンをハードコードで握り潰さない。精度優先（**偽FAILを出さない**、取りこぼしは他ゲートで補う）。
- 症状ごとのBlueprint追加をしない。form/difficultyは構造で直す。
- **作業分担: Opusで思考・設計・レビュー、Sonnet（サブエージェント）で実装。** Opusが分解・指示→Sonnetが実装・逐次コミット→Opusが検証。
- **サブタスクごとに逐次コミット**（レート制限で中断しても失わない）。push はユーザーが明示依頼するまでしない。
- **アカウント切り替えは双方向**（レート回復後に元アカウントへ戻る）。マイルストーンごとに**この HANDOFF を更新・コミット**し、
  どちらのアカウントからでも最新状況を追えるようにする（§冒頭の運用ルール参照）。**この更新徹底が最優先規律**。
