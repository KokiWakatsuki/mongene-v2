## 2. システム構成（3段パイプライン）
1. **①計算骨格生成**: `Blueprint`（問題の型）＋`Atom`（Noun=図形/数, Verb=操作、SymPyで計算）が `MiddleRepresentation`(MR) を作る。
2. **②LLM翻訳**: `LLMTranslator`（Gemini `gemini-flash-lite-latest`）が MR を自然言語の問題文・解説へ翻訳。
3. **③図レンダリング**: `visual_dsl` を SVG 化。
- `master_data/mapping.json`（184レッスン）が各レッスンに Blueprint・`difficulty_levels`・`required_tags` 等を紐付ける中心データ。
- エンドポイント: `/problems/inspect`（POST, **LLM翻訳前の生MRを返す＝LLMフリー**）、`/problems/generate`（①②③通した最終問題＝実LLM）。
- Python 実行は必ず `.venv/bin/python`（system python に sympy 無し）。テスト: `SKIP_LLM_IN_TESTS=true .venv/bin/pytest tests/ -q`。

## 3. 伸び悩みの診断（Opusによる設計レビュー）
**2つの構造問題**:
1. **計算骨格ファーストを全形式に強制**: SymPy数値骨格→LLM翻訳は `calculation` には最適（SymPyが正しさを保証＝moat）。
   だが `word_problem/proof/knowledge/visual` にも同型を強制し依存が逆。form/difficulty が「骨格への後付けスタイル指示」に堕し
   生成の構造を決めていなかった。
2. **評価ループの空回り**: 評価が `/inspect`(LLM前) かモックに対してで**偽陰性**。修正打点が症状レベル（Blueprintを11→17個と線形追加）。
   固定の参照正解セットが無く改善が測定不能だった。

**打ち手**: ①非計算形式は「骨格→翻訳」から「**生成してから検証(generate-then-verify)**」へ反転。
②評価を**実出力×決定論ゲート**に固定。オペランドジッターの難易度を構造ベースへ。

## 4. 中核戦略（ユーザー制約を満たす設計）
- **評価の原則（コスト効率）**: **数学的に検証できる評価は決定論で**（math-verifiable にLLMを浪費しない／クォータ有限／再現可能・無料）。**LLMでしか評価できない意味的質（題材忠実性・自然さ・意味的難易度）にはLLMを使う**（これらは決定論では測れない＝G6で確認）。LLM-judge を避けてきたのは主に**生成器と同一モデルで判定する循環**の回避で、別モデル(Opus)がオフラインで判定するのは可。**LLMは有限なので全体評価（広く安く候補特定）と個別評価（絞って深く判定）を使い分ける**（§17.0）。
- **生成は稀・評価は毎回**の非対称: 実LLM出力(product)は1回だけ生成・凍結し、決定論ゲートは毎回それに対して走らせる。
- **evaluator = verifier**（設計の背骨）: フェーズ2で作る決定論ゲートを、フェーズ3で生成時の受理／棄却フィルタに昇格させる。評価作業を捨て駒にしない。
- SymPyが計算した数値・答えは**絶対に変更しない**（moat）。
- **症状ごとのBlueprint追加で握り潰さない**。form/difficultyは構造で直す。

### 17.0 評価の原則（ユーザー・全体評価と個別評価の使い分け）
「評価にLLMを使わない」は **LLM-judge の全面禁止ではない**。正しくは:
- **数学的に検証できるものは決定論で**（math-verifiable にLLMを使うのは勿体無い＝クォータ浪費）。
- **LLMでしか評価できない意味的な質（題材忠実性・文章/図の自然さ・意味的難易度）にはLLMを使うべき**
  （決定論では測れない＝G6で確認）。
- **LLMは有限**なので浪費せず、**2種類を使い分ける**:
  - **全体評価（whole/broad）**: コーパス全体を**安く広く**見て問題箇所を**特定（triage）**する。手段＝
    決定論の構造スキャン（LLMフリー）＋必要なら粗いLLM一括パス。目的＝どこを深く見るかの絞り込み。
  - **個別評価（individual/deep）**: 絞られたセルを**LLM(Opus)で深く判定**し修正設計。予算を要所に集中。
- **回し方**: 全体（安く特定）→ 個別（高く判定）→ 修正 → 再全体、を反復。LLM予算を無駄にしない。
- LLM-judge を避けてきた本来の懸念は**生成器と同一モデルで判定する循環**の回避で、別モデル(Opus)が
  オフラインで判定するのは可。決定論ゲート(G1-G7)と ground truth は引き続き LLMフリー。

### 17.1 なぜ今まで着手していなかったか（真因）
1. **評価対象の誤分類（最大）**: 「評価にLLMを使わない」を"LLM-judge 全面禁止"と過剰解釈し、本来
   **LLMでしか評価できない意味的質（題材・自然さ）まで決定論ゲート（G6等）で測ろうとし続けた**→測れず
   空回り（G6で「大小/符号を除外する fingerprint では難易度を測れない」限界を確認）。正しくは §17.0＝
   math-verifiable は決定論、意味的質はLLM(Opus)を全体/個別で使い分け。**意味的質の監査に Opus を使うのは原則通り**。
2. **「監査には翻訳済み product が要る＝LLM大量生成が要る」という思い込み**でクォータ待ちに見え後回し。
   実際は**題材ミスマッチの大半は /inspect の MR（LLMフリー）で見える**（例: 反比例なのに
   operation=arithmetic、g3_l32が intersect、g3_l45が単一 measure_area、旧MovingPointが静的面積）。

4. 個別のLLMフリー修正（契約・図・凍結解除）が満足度高く、系統監査に着手しなかった。
