5. **params 忠実性契約は表示にも効く。** `y = x²` は係数 1 を表示しないので、
   `numbers` に a=1 を置けない。表示に現れない値は候補から外す。

### この束で確定した設計判断

1. **「自分で選べ」は、どれを選んでも同じ結論になるデータを構成して成立させる。**
   指標を engine が固定すると設問が変わる。平均値・中央値・最頻値がすべて同じ側を
   指すデータだけを作れば、「自分で選んでよい」がそのまま成り立ち答えは一意になる。
2. **判断を問うセルは params が「場面の種類」だけになり dup が通らない**
   （実測 0.90〜0.98）。答えの根拠を変えない数値（母集団の大きさ）を第2軸に足す。
3. **checker は mode を params から読む。** params の形（どのキーがあるか）から
   セルを推測すると、似た形のセルが増えたときに黙って別の solver を呼ぶ（実際に踏んだ）。
4. **本文に出る数はすべて `numbers` に置く。** データ列を別キーに逃がして `numbers` を
   空にしたら、契約テスト（numbers が空なら本文に算用数字が無いこと）に落ちた。
   列は `numbers` に載せ、checker はそこから組み直す＝二重管理にしない。

4. **証明したい定理は規則から外す**（`exclude_rules`）。外さないと循環して1手で終わる。

## 進め方の運用ルール（踏んだ事故の再発防止）

1. **worktree の基点確認を必ず最初にやらせる**
   （過去に旧 master 基点で作られる事故が複数回。ずれていたら `merge --ff-only` で揃える）

   → `scratchpad/check_cell.py` の 100seed 実測が本物
3. **ゲートは答えが 0 や 1 に潰れる退化を素通りする**
   → property テストで固定する
4. **eval は「テスト緑」とは別に必ず回す**
   （fingerprint が op 列なので Lv 間で op 列が同じだと level_sep が黙って壊れる）
5. **check_cell が ALL_OK でも pytest 全走は別に必要**（2026-08-07 に2件踏んだ）
   - `frames.py` の `asked_vocab` を増やしたら `test_frames.py` の台帳 frozenset にも足す
   - word_problem は `params["numbers"]` 必須・値はすべて本文に現れること

     併せて検査する）
6. **level_sep は「何を文字に置くか」を動かすのが一番効く**
7. **params は「本文に出ている数値」だけ**（導出値を置くと検証に穴があく）
8. **並列度は3〜4体**。競合面は `concepts.yaml` と各 `__init__.py` のみ（追記）なので
