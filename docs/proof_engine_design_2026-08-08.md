# 証明・作図エンジンの設計（2026-08-08）

> 決定: **手書きのセルを並べるのではなく、構成生成器＋前向き推論器で作る。**
> 理由は「このシステムは無限に問題を生成する。無限には、数値が違う問題だけでなく
> **解き方が違う問題・この世にまだない問題**が含まれる」という前提（ユーザー確定）。
> 優先順位は ①問題文・図・解説の質 ②コストの低さ ③応答速度。
> 質の基準は「市販の問題集・入試と同じもの」。

## 0. なぜ手書きでは足りないか（既存 570 セルの限界）

既存セルは `scenario_kind` / `mode` というパラメータで解き方を切り替えているが、
**その選択肢は人が手で並べた分だけ**である。数値と場面は無限でも、**解き方の種類は有限**で、
増やすには 1 つずつ書く。証明 51 セルを同じやり方で作れば、この限界を 51 セル分固定する。

## 1. 全体の形

```
① 構成生成器（作図的生成）   点・線・円を「作図手順」で組み立てる
                            座標は手順から厳密値で決まる ＝ 必ず実現可能で自然な図
                            **事実は構成手順が持つ。座標から測って事実を作らない**

② 事実の集合                構成が生む述語を列挙（equal_length / equal_angle /
                            parallel / perpendicular / midpoint / collinear /
                            congruent / similar …）

③ 前向き推論器              規則カタログ（中学範囲の定理だけ）を適用できる限り繰り返し、
                            導ける事実を飽和させる。導出は DAG（事実 ← 規則 ← 前提）

④ 問題の切り出し            DAG の到達点から結論を選び、**最短導出**を模範解答にする
                            仮定を削る／足すと難易度が変わる

⑤ 証明文の生成              導出パス →（主張, 根拠）の列 → テンプレートで日本語化
                            **LLM は使わない**（証明文は定型。LLM は型を崩して質を下げる）
```

### なぜ無限になるか
- 同じ図でも**結論を変えれば別の解き方**（DAG の別の到達点）
- **構成を変えれば必要な定理が変わる**（合同で解ける図／相似が要る図／円周角が要る図）
- 構成の組合せは無限 ＝ 人が思いつかなかった配置も出る

### なぜ質が保てるか
- **規則カタログが中学範囲の定理だけ**なので、出てくる証明は必ず教科書の範囲に収まる
- **導出が engine の中にある**ので、模範解答は原理的に常に正しい。内部検証は
  「各行が規則どおりに適用されているか」を見るだけで決定論に閉じる
- **座標は作図手順から決まる**ので、つぶれた三角形・ありえない配置が原理的に出ない

### 難易度と補助線の機械的な定義
| Lv | 定義 |
|---|---|
| Lv2 | 導出の深さ 1（仮定から 1 つの合同条件で直接） |
| Lv3 | 導出の深さ 2、または**補助線が必要**（構成に要素を 1 つ足すと導出が閉じる） |
| Lv4 | 深さ 3 以上／複数の合同を組む／着目すべき三角形の候補が複数ある |

台帳の proof Lv3 の desc がほぼ全部「補助線」なのは、この定義とぴったり合う。

## 2. 作図（construction 9セル）も同じ機構

作図問題は「与えられた要素から、**定規とコンパスの基本操作**で目標を得る」＝
**操作カタログが基本作図5種になっただけの同じ前向き探索**。構成生成器はもともと
作図手順で図を作るので、**その出力をそのまま作図問題にできる**。
→ 51 + 9 = 60 セルが 1 つの投資に乗る。将来は角度追跡・線分比・面積の求値にも効く。

## 3. LLM の置き場所（生成経路の外）

| 用途 | LLM | 呼ぶ場所 |
|---|---|---|
| 証明の正しさ | **使わない** | engine 決定論（配置から導ける・LLM は自信ありげに間違える） |
| 証明文・解説の文面 | **使わない** | 定型なのでテンプレートの方が質が高い |
| 場面文のカタログ増産 | 使う | **オフラインのバッチ**→人が検査→カタログに固定→生成時は決定論 |
| 意味ズレ検査（G-BT） | 使う | 夜間/CI のバッチ全走査。**証明・作図には場面文が無いので対象外** |

生成時の LLM 呼び出しは **0 回**（コスト 0・応答はミリ秒）。

## 4. 探索の副作用に対する質のフィルタ（ここが質の本体）

探索は「解けるが人が作らない問題」も出す。次を決定論で弾く。

- 結論が聞く価値のある命題か（自明・冗長を弾く）
- 単元に合った定理を使っているか（二等辺の単元で円周角を使う証明を弾く）
- 導出が最短か（遠回りな模範解答を出さない）
- **図の品質ゲート**（新設）: ラベル衝突・頂点間の最小距離・角の下限・枠内・
  図の要素が問題文の記述と一致
  ——この一連で図のバグを 4 件目視で見つけた。証明では図が複雑になるので機械化が要る

### 4.1 質のフィルタは「図に描かれているもの」だけを見る（2026-08-09 追記）

実装当初、`figure_quality_problems` は**全3点組**の角を、`accidental_coincidences` は
**全点対**の長さと全角を見ていた。これが単元の展開を止めていた。

- 平行四辺形ABCDの辺の中点Mについて ∠ACM（CM は線として引かれていない）が
  18°を割る、という理由で図が落ちる
- 引かれていない線分どうしの長さがたまたまそろっている、という理由で構成が落ちる

中点連結定理・ピラミッド型・平行四辺形の辺の中点という**教科書の定番の図は、
この2つでことごとく落ちていた**（通過率 0/48）。検査対象を「線として描かれている
線分」と「2辺とも描かれている角」に限ったら 39〜45/48 になり、7セルが一気に開いた。

理屈は単純で、**図に見えていない性質は、生徒には存在しない**。「たまたま等しく
見えている」も「つぶれて見える」も、見えていることが前提の話である。

### 4.2 定義域は測って決める（同）

`check_cell` は rejects=0/120 を要求し、recipe の有界リトライは 24 回。合格率が 9 割を
切ると 120 本のどこかで必ず落ちる——が、**狭くて合格率の高い箱より、広くて合格率の
低い箱がよい**。24 回引き直せば rejects は 0 になるが、dup_rate は箱の広さでしか
下がらないからである（g2_l47 Lv2 が 112 通りの箱で dup 0.37 → 広げて 0.04）。

道具は2つ。
- `scratchpad/probe_constructions.py` — 構成ごとに、深さ×prefer で何が結論に選べるかを
  **op 列つき**で一覧する（family の proof_depth / prefer はこれを写すだけになる）
- `scratchpad/fit_domain.py` — 合格する箱を貪欲に探し、family に貼る形の定義域を出す

### 4.3 点を増やしても深い証明は出ない（同）

6点の図で `saturate` が飽和しなくなった（上限 12 ラウンドに対し 24 ラウンド・
事実 6221 個）。合同の対応が組合せで膨らむためで、点を足すのは筋が悪い。
**同じ図で結論の深さを1段ずらす**ほうが、Lv 差としても素直に出る
（合同を示す → 対応する辺が等しい）。

## 5. モジュール構成

```
engine/packs/math/geometry/
  facts.py        述語（正規形・ハッシュ可能）
  construct.py    作図的構成（op → 点の厳密座標 ＋ 生まれる事実）
  rules.py        規則カタログ（前提パターン → 結論 ＋ 根拠の日本語）
  deduce.py       前向き推論（飽和）・導出 DAG・最短導出の取り出し
  naturalness.py  質のフィルタ
  render_text.py  導出 →（主張, 根拠）の列 → 証明文
```

答えの型は `ProofAnswer`（構造つき証明＝(主張, 根拠) の順序つき列 ＋ レンダリング済み
証明文）を `core/contracts.py` に追加する。既存 570 セルには触らない追加のみ。
`PROOF_FRAME` は既に `asked_vocab={"proof_text"}` を宣言しているのでそのまま使える。

**採点 LLM への利点**: 模範解答を自由文で渡すより、「根拠の列」を構造で渡せる方が
生徒の記述との照合がぶれない。

## 6. 刻み方

1. **合同系だけの最小カタログ（10 規則程度）で機構を 1 本通す**
   構成生成 → 推論 → DAG から証明文 → 図 → 品質フィルタ を、この範囲で全部動かす
2. 出てきた問題を実物（市販問題集・入試）と突き合わせ、質のフィルタを詰める
3. **規則カタログを増やして**相似・円周角・平行線・等積変形へ広げる（機構は触らない）
4. 操作カタログを基本作図 5 種にして作図 9 セルを出す

進捗（2026-08-09）: 1〜4 すべて済み、**proof 51/51・construction 9/9（全体 630/630）**。
単元クラスタごとに `rules_*.py` / `constructions_*.py` を分けてあるので、並行して足せる。

- 作図9セルは §2 の見立てどおり構成生成器の出力をそのまま問題にして開いた
  （`recipes/construction.py`・答えは `GraphAnswer`）。
- 文字式による説明6セルは、図形とは別機構の `solvers/number_proof.py`
  （型＋パラメータの命題を sympy に展開させ、**示すべき性質も式から導く**）で開いた。
- **form が proof でも、機構は3つに分かれた。**「図の上の事実を前向きに増やす」（deduce）で
  書けるのは合同・相似・円周角までで、残りは形が違う:
  - `solvers/conditional_proof.py`（g2_l38）… 仮定と結論を分けた命題を作り、
    **真偽を判定する**（正しくない命題も作り、反例を探す）。中心は導出でなく判定。
  - `solvers/pythagoras_proof.py`（g3_l51/l52）… 図の分け方から**同じ面積の2通りの
    表し方**を作り、差を sympy に取らせて a²+b²-c² の定数倍かで「その図で示せる」を
    判定する。式変形そのものが証明になる。逆（g3_l52）はピタゴラス数から3辺を引く。
- **面積の恒等式は分け方の抽象しか見ない。** 台形（Garfield）の図で、高さの辺を分ける
  点の位置を取り違えて（上底の側から a と書いていた。正しくは b）も、恒等式の検証も
  数値検算も素通りした。**図の記号の付け方は、代数の検証の外側にある**——座標を置いて
  長さを数で当たるまで見つからない（a=3, b=4 で FI=√18、IG=√32）。
- **誘導ありの問題文は、答えが使う記号をすべて名づけていること。** 面積証明の誘導あり側は
  内側の図形を記号で呼ぶ（「正方形EFGHの面積は c²」）ので、問題文が EFGH を導入して
  いないと、答えに出どころのない記号が現れる（`_guided_setup`）。

**規則カタログに定理を 1 つ足すと、それを使う問題が全部出てくる**——これが本当の償却。
