1. ミッションと最終ゴール

最終ゴール（北極星） 全ての学生が、自分で課題を発見できる能力を養うこと。
本エンジンはそのための教育システム（Education OS）の一部品＝Layer 1 教材AI の問題供給部である。

1.1 「自分で課題を発見する」がエンジン要件に落ちる糸

生徒フロー設計（設計図③）は、システムが診断を与えるのではなく、生徒が自分で誤りを特定するよう組まれている：

  1. 誤答時は○×のみ表示（答え・解説をすぐ見せない）
  2. 生徒が自分の解答（撮影画像）の間違えた箇所に自分で赤丸を移動する（「わからない」も選べる）
  3. なぜ間違えたかを選択肢から自分で選ぶ（例: 二次関数のステージで「一次関数だと思った」）
  4. 選んだ原因に対応する戻り先（再インプット／一次関数／四則演算／グラフ読み取り／ケアレスミス訓練）へ移動し、そこで問題を解いて仮説を検証する

この営みが成立するために、エンジンには次が要求される（→ 対応する機能要件）：

学習設計上の仕掛けエンジンへの要求要件
○×のみ→段階的に開示答え・途中過程・解説・ヒントを分離した部品として返し、開示タイミングをホストが制御できるF-8, F-9
原因の選択肢を提示単元ごとの誤答要因の語彙と、問題への要因タグ付けF-7・F-11・カリキュラムモデル（§3②）
戻り先で仮説検証原因→前提単元の座標を解決し、その場で戻り先問題を供給F-7
できるまで出続ける無限供給（数値・題材が変わる同型問題）＝完全習得学習の前提条件F-3, F-4

1.2 事業文脈（なぜ無限供給か）

  • Bloom の完全習得学習（2σ）: 習得判定（BKT 85%・直近5問80%・3問連続正解）を回すには、判定のたびに新しい問題が要る。既存問題集では枯渇する——無限性は飾りではなく mastery learning の前提。
  • 先生の時間の解放: 指導時間の25%が「問題を探す時間」に消えている（未踏提案書）。エンジンは探す時間をゼロにし、先生を「生徒に向き合う」役割へ返す。
  • 授業経験ゼロ採用（Education OS の核）: 問題作成・採点・分析をシステムが持つことで、先生の学力依存を解消する。エンジンの品質保証はその土台。
  • 北極星KPI＝継続率85%: エンジンの寄与は「生徒に合う問題が途切れず出る」「問題切れ・破綻問題ゼロ」。

2. エンジンが仕える学習ループ（ユースケース）

設計図3枚と未踏提案書のサイクル「採点・苦手分析 → FB＋対策問題生成 → 生徒が解く」を、エンジン視点のユースケースに翻訳する。エンジンの要件はすべてここから導出される。

UC-1 ステージ進行（授業の背骨）
流れ
インプットフェーズ（公式を書く・説明できる）→ ベース問題 → 正解 → 最終問題 → 正解 → ステージクリア
エンジンへの要求
単元×難易度段に対するベース問題の供給。単元の必須要素を全て含む最終問題（＝これが解けたら単元クリアと言い切れる合成問題）の供給。
UC-2 誤答からの戻り（自己課題発見の核）
流れ
誤答 → ○×のみ → 自分で誤り箇所マーク → 原因を選択 → 原因に応じた戻り先の問題へ → クリアで復帰
エンジンへの要求
誤答要因（例:「一次関数だと思った」）から戻り先座標を解決し、そこの問題を即時供給。知識グラフを遡った根本原因の問題（例: 空間図形の躓き→三平方→因数分解）。
UC-3 宿題生成
流れ
授業内で終わらない→残りが宿題／原因再選択で授業終了→その時点で生成された問題が宿題になる
エンジンへの要求
「何を宿題に残すか」の判断はホスト。エンジンは構成表を受けたセット組成（F-13）と、紙に印刷できる出力（問題・図・解答が紙ワークフローに耐える）を担う。
UC-4 類題再生成（モンジェネETSUZAN版の継承）
流れ
解き直したい問題に対し、A: 数値のみ変更（ケアレス克服）／B: 文脈を変更（定着確認）／C: 問われる内容が異なる（解法戦略の強化）
エンジンへの要求
基準問題を指定した3モードの類題生成。A=同構造・数値再抽選、B=同構造・題材/文脈差し替え、C=同概念・別構造。
UC-5 先生ダッシュボード連携（Layer 2）
流れ
先生は生徒の進捗（インプット/解答/採点/要因選択の4フェーズ＋経過時間）を監視。詰まった生徒に段階ヒント1を開放。
エンジンへの要求
問題に付随する段階ヒント列（少しずつ核心に近づく複数段）。解説とは別部品であること。
UC-6 カリキュラム並べ替え（ロードマップ）
流れ
学習指導要領ベースのロードマップを、生徒が持ってきた教科書の目次で並べ替え。学校・地域ごとに最適化。指導要領改訂（高校内容が降りてくる等）にも追従。
エンジンへの要求
単元は順序に依存しない独立部品であること（並べ替えはホストの自由）。単元の追加・分割・移動がデータ変更のみで済むこと。
UC-7 採点・苦手分析との結合（Layer 1 内の相方）
流れ
採点エンジン（手書き答案の撮影→途中式レベル採点→エラー4分類: 読解/変換/処理/書き写し）→ 苦手プロファイル → 次の問題生成へ
エンジンへの要求
採点が参照する模範解答＋途中過程を機械可読で出力。問題・小問への概念タグ（BKTが習得度を概念単位で追跡するための鍵）。
UC-8 模試対策（将来）
流れ
志望校の出題傾向・難易度構成を解析し、本番と同一構成の模擬テスト一式を生成（未踏提案書の第3モード）
エンジンへの要求
複数座標のセット組成（構成表→問題一式）。将来は問題DB（IRT較正済み）とのハイブリッド供給。

3. 製品定義と責務の3分割

本エンジンは「問題供給エンジン」である：座標と目的を渡されたら、正しさが保証された問題（問題文・図・答え・途中過程・解説・ヒント・タグ）を1件返す装置。生成はその主要な実現手段だが、契約上は供給源（生成器／将来の問題バンク）を抽象化する。

周辺システムとの境界を3つに分割する。過去の混乱の一因は、この3つが未分化だったこと（単元定義・難易度・誤答要因のような「教育の知識」が、生成コードの中に埋没していた）。

① 問題供給エンジン（本書の対象）

  • 契約: generate(座標, 目的, seed) → Problem
  • 正しさ・形式・難易度・図の品質保証
  • 供給可能座標の告知（capabilities）
  • 類題3モード・段階ヒント・概念タグ付け

② カリキュラムモデル（共有データ資産）

  • 単元タクソノミー（科目×単元×形式×難易度段）
  • 知識グラフ（前提関係DAG）
  • 誤答要因の語彙と要因→戻り先座標の対応
  • 単元クリア基準（最終問題の要素定義）
  • エンジンとホストの共通言語。教育者（高橋）が編集できる形式

③ ホスト（スコープ外・Education OS 各層）

  • 採点エンジン（手書き採点・エラー分類）＝舛田
  • 適応学習（BKT/FSRS/IRT・苦手プロファイル）
  • 授業OS（ステージ進行・先生ダッシュボード）
  • 生徒UI・印刷・通知＝小武
  • インプットフェーズ素材（公式・説明教材）の提示 ※素材の出所・整備はカリキュラムモデルの論点＝D-5
境界の原則 「生徒が今どこにいて次に何をすべきか」を決めるのはホスト（適応学習）。エンジンは決められた座標・目的に対し最良の1問を返すことに徹する。ただし判断の材料（概念タグ・要因タグ・難易度メタ）はエンジンが全問題に付与する。カリキュラムモデルは両者が参照する辞書であり、コードから独立したデータとして管理する。概念単位の絞り込みが必要なとき、ホストは options.target_concepts で要求できる（「判断はホスト・供給はエンジン」の分担は変えない）。

4. ドメインモデルと生成契約

4.1 生成リクエスト（エンジンAPI＝製品そのもの）

generate(request) → Problem | Unsupported(理由コード)
  // 理由コード語彙: 座標不在 / form非対応 / level非対応 / 検証全滅(F-14) / 供給枯渇

request = {
  subject : "math"                     // 科目（科目パックの選択）
  unit    : "g3_l51"                   // 単元（カリキュラムモデルのID）
  form    : "find_value"               // 問題形式（科目パックが定義。数学=7型）
  level   : 2                          // 難易度段（band絶対値: 基礎1/標準2/応用3/発展4）
  purpose : "base"                     // 目的: base | final | remedial | variant
                                       //（宿題・模試は1問APIではなくセット組成 F-13 のセット種別）
  seed    : 12345                      // 再現用乱数種（省略時=毎回異なる）
  options : {
    cause_id        : "confused_with_linear"   // remedial時: 誤答要因ID（語彙の正=カリキュラムモデル）
    target_concepts : [concept_id...]          // 概念単位の絞り込み（BKTのピンポイント要求・任意）
    variant_of      : {problem_ref, mode:"A|B|C"}  // variant時: 基準問題と類題モード
    avoid           : [problem_ref...]             // 既出回避（同一性の定義=D-1）
  }
}

4.2 Problem（出力契約）

Problem = {
  problem_text   : 問題文（答え非含有・自然な日本語）
  visual         : 図/グラフ/表（形式が要求する場合のみ・答え非含有・紙印刷可）
  sub_questions[]: {
    label, prompt_text
    answer        : { 正答(記号厳密形), 表示形, 型 }      ← 決定論的に検証済み
    solution_steps: 途中過程（採点エンジンが途中式採点に使う粒度）
    explanation   : 解説（steps に忠実な翻訳）
    hints[]       : 段階ヒント列（開示順に複数段）
    concept_tags[]: カリキュラムモデルの概念ノードID     ← BKT・知識グラフ遡りの鍵
    cause_tags[]  : この問題が検証できる誤答要因ID
  }
  meta           : { 座標, purpose, seed, 生成器ID/版, problem_ref, 再現情報 }
}

重要: answer / solution_steps / explanation / hints は分離した部品。ホストが「○×のみ→ヒント1→ヒント2→解説」の開示順を制御できる（§1.1）。「部品の分離」とはテキスト内容を他部品に内包しないことの意（ID参照は可）。

problem_ref（一意参照）の定義: {座標, purpose, seed, 生成器ID＋版, 翻訳キャッシュキー} の組。variant_of・avoid・F-2再現・F-17監査の4機能が共通で使う。決定論の境界: 計算骨格（数値・答え・途中過程）は seed で完全再現し、文章化（LLM翻訳）は翻訳キャッシュを再現情報に含めることで再現する。

4.3 座標系の正

数学の座標系（184単元×形式7型×band絶対Lv・各段の構造定義・例・市販位置づけ）は確定済み資産 docs/input_spec_2026-07-08.json を初版とし、カリキュラムモデルへ昇格させる。知識グラフ・誤答要因・クリア基準は未整備＝カリキュラムモデルの拡張として整備する（§10 M1）。

注意: セルごとの有効な form×level は疎である（全単元が7型×4段を持つわけではない。例: knowledge が Lv1-2 のみの単元がある）。有効セルの正は capabilities（＝カリキュラムモデル）が返すものとする。

5. 機能要件（F）

優先度: MUST=無いと学習ループが回らない ／ SHOULD=品質・運用上強く必要 ／ MAY=将来。 フェーズ（§10）: M0金の縦串 M1知人塾MVP M2v1.0 M3実証・拡張

A. 生成コア

ID要件受け入れ基準優先度導入
F-1生成契約: §4.1/4.2 のAPIを提供。全部品（答え/途中過程/解説/ヒント/タグ）が揃った構造化データを返す対応座標で全フィールドが非空。スキーマ検証に合格MUSTM0
F-2決定論・再現性: seed 指定で同一問題を再現。障害報告・回帰・監査の前提計算骨格は同 seed 2回で同一。文章化は翻訳キャッシュ込みの再現情報（§4.2 problem_ref）で再現できるMUSTM0

M2(B/C)
F-5未対応座標の明示拒否: 供給できない座標は理由コード付きで拒否。受理して別種の問題を返すことを禁止（現行最大の欠陥）未対応座標→Unsupported応答。別形式・別題材の問題が返るケース0件MUSTM0

B. 学習ループ支援（本書v2で新規——設計図・未踏提案書由来）

ID要件受け入れ基準優先度導入
F-7戻り先問題（remedial）: 誤答要因IDを受け取り、カリキュラムモデルに定義された静的対応（要因→戻り先座標）を解決して問題を供給。知識グラフをどこまで根本へ遡るか（習得度依存の判断）はホストの責務——エンジンは生徒データを持たない（N-8）カリキュラムモデルに定義された全要因で問題が返る。返る問題の概念タグが要因の対象概念と一致MUSTM1
F-8段階ヒント: 各小問に、核心へ段階的に近づくヒント列（2段以上）。解説とは独立の部品ヒントが答えを直接含まない（漏洩検査）。各段が前段に無い新情報を1つ以上含む（V4 サンプリングで確認）SHOULDM1
F-9段階的開示に耐える部品分離: 答え/途中過程/解説/ヒントを別部品で返す（○×のみ→自己発見のUXの前提）ホストが任意の開示順を組める（部品間に埋め込み参照がない）MUSTM0
F-10最終問題（final）: 単元クリア基準＝「必要な要素を全て満たす合成問題」を供給。クリア基準はカリキュラムモデルが定義final の概念タグ集合が、単元のクリア基準要素集合を被覆するSHOULDM2
F-11概念タグ・要因タグ付け: 全問題・小問にカリキュラムモデルの概念ノードID（BKT習得度追跡の鍵）と、その問題が検証できる誤答要因ID（cause_tags）を付与タグ無し問題0件。タグはカリキュラムモデルに実在するIDMUSTM1
F-12採点適合: solution_steps が採点エンジン（手書き途中式採点・エラー4分類）の要求粒度を満たす。answer は記号厳密形＋表示形の両建て採点エンジンとの結合テストに合格（スキーマは舛田と共同設計＝D-2）MUSTM1
F-13セット組成: 宿題・小テスト・模試などの構成表（座標×問数×配列）から問題一式を組成構成表通りのセットが返り、セット内重複がないSHOULDM2

C. 品質・検証

ID要件受け入れ基準優先度導入
F-14generate-then-verify: 全出力は検証ゲート（§6）を通過したものだけ。ゲート全滅時は Unsupported を返す（壊れた問題を出すくらいなら出さない）ゲート素通り経路が存在しない。破綻問題の流出0（監査で計測）MUSTM0
F-15形式・難易度・題材の忠実性: 出た問題が選んだ form/level/unit の定義（カリキュラムモデル）に一致（§6 Q2-Q4）Q2-Q4 の検査に合格MUSTM0
F-16図の従属・非漏洩: 図は形式が要求するときだけ。図・問題文に答えを含めない漏洩の定義＝「問題を解かずに答えが読み取れる」。機械検査は除外規則（式中の係数・軸目盛等）を仕様化した上で図中文字列・問題文・ヒントを検査（素朴な文字列一致は偽陽性の山になるため不可）MUSTM0
F-17品質監査ループ: 意味的品質（題材忠実・自然さ）を LLM 監査で定期スキャンし、劣化を検知・修正する運用が組み込まれている監査レポートが再現可能（seed付き）で、修正が回帰テスト化されるSHOULDM1

9. アーキテクチャ方針（失敗診断と設計原則）

9.1 なぜ実装が失敗し続けたか（正直な診断）

結論から：blueprint×atom という発想自体は誤りではない（組合せで無限性を得る・追加のみで拡張する、は本書でも F-3/F-19 として維持）。失敗の真因は発想ではなく、次の4点にある。

#真因何が起きたか
1要件の不在「何ができたら完成か」（本書のQ）が定義されず、実装は「とにかく生成が通る」ことに最適化された。ゲートは「壊れていない」ことは保証したが「意図通り」であることは誰も測らなかった
2著作単位の粒度ミスマッチ（最大）教育的な意図の単位は「単元×形式×難易度段」のセル（約1,000セル）なのに、実装の単位は27個の Python クラス（blueprint）だった。1クラスが数十セルを兼務した結果、セルごとの意図を書く場所がどこにもない。「同じ問題ばかり出る」「難易度を上げても構造が変わらない」「形式を無視する」は全てこの帰結
3意図の非伝搬形式・目的・難易度が生成パイプラインの末端（図・翻訳）まで届かず、図が形式を無視して常に描かれ、答えまで図に書かれた
4教育知識のコード埋没単元定義・難易度の意味・誤答要因といった「教育の知識」がコードと設定に散在し、教育者がレビュー・編集できなかった（＝イメージが実装者に伝わらない構造）

9.2 設計原則（要件から導出）

P1 薄いコア・科目非依存 — コアは契約の解釈器＋検証枠組み＋翻訳/監査基盤＋プールのみ。科目・単元・題材の知識を持たない（F-18）。
P2 著作の単位＝セルに紐づく宣言的スペック — 「この単元・この形式・この段の問題はこういうものだ」を書く場所を、コードでなく宣言的データ（問題族スペック）として1セル単位に持つ。教育者が読める形式にする（真因2・4の直接対策）。
P3 部品は共有ライブラリ — 題材部品（atom）と解法・検証部品（solver/verb）はスペックから参照される共有資産。部品追加で全スペックの生成空間が同時に広がる（F-19。blueprint×atom の正統な継承部分）。
P4 意図の全層伝搬 — 座標・目的は Problem 完成まで全段に渡り、図・翻訳もそれに従属する（真因3の対策・F-15/F-16）。
P5 検証を通ったものだけが存在する — generate-then-verify。検証器（V1〜V3）はパックが宣言し、コアは枠組みだけ持つ（F-14・§8）。
P6 カリキュラムモデルの独立 — 教育の知識（単元・知識グラフ・誤答要因・クリア基準）はエンジン外のデータ資産。教育者が編集し、エンジンとホストが共有参照する（§3）。

blueprint×atom との関係：atom（部品）と verb/solver（解法・検証）はそのまま生きる。変わるのは blueprint の実装形——「Python クラス」から「宣言的な問題族スペック（データ）＋それを実行する小さなコア」へ分解する。これにより：

  • セルごとの教育的意図に書く場所ができる（1スペック=1〜数セル。1クラス=数十セルの兼務が消える）
  • スペックはデータなので、教育者がレビューでき、LLM に下書きさせて人が検収する制作フローが組める（約1,000セルのスケール手段）
  • 「追加のみで拡張」がむしろ強まる（スペック追加=ファイル追加。コード修正なし）
