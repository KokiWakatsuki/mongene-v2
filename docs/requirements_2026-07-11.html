1. 背景と経緯

本システムは4世代の試行を経ている。各世代で「何が得られ、何が課題として残ったか」が現行設計の根拠である。

世代アプローチ得られたもの残った課題
①チャットで生成AIに問題を直接作らせる 問題自体は生成できる 難易度のコントロールが微妙・図の精度が低い
②問題そのものではなく Pythonコードを生成させ、コードが図を描く 図の質が安定 生成コストが高い
③問題PDFを入力し類題を生成 既存問題に似た問題が作れる 生成コスト＋元の問題がないと生成できない
④
(現行)		blueprint（問題構造）× atom（部品）の組合せ生成。正解は SymPy が決定論的に計算 元問題不要・正しさが機械保証・追加作業だけで生成空間が爆発的に増える設計 設計思想が実装に正しく伝わらず、形式忠実性・難易度分離・図の従属性が未達 ← 本書の動機
本書が解決するメタ問題 これまで失敗が繰り返された根因は2つ。(a) 「何ができたら完成か」の定義（受け入れ基準）が無かったため修正が場当たりになった。(b) 世代④のコアコンセプト（追加のみで拡張する組合せ設計）が実装者に伝わる形で文書化されていなかった。本書は (a) を §6–7 の要件表で、(b) を §3 で固定する。

2. 製品定義とスコープ

mongene-v2 は、教育システムに組み込まれる「問題生成エンジン」である。 「問題が確定していない問題集」は完成イメージの比喩であり、実体は API 部品。直接の顧客は生徒ではなくホスト（周囲の教育システム）であり、生徒はホスト越しにエンジンの出力に触れる。

2.1 エンジンの中心契約（＝製品そのもの）

generate(unit, form, level, seed) → Problem
   unit  : 単元（レッスンID。例 g3_l51）
   form  : 問題形式（7型。§6 F-2）
   level : 難易度段（band絶対Lv。基礎1/標準2/応用3/発展4）
   seed  : 乱数種（指定→決定論的に同一問題／省略→毎回異なる問題）

   Problem : 問題文・小問列（解答＋解説）・図（form が要求する場合のみ）・メタ情報
             の構造化データ。ホストが機械的に扱える。

エンジンの価値はこの契約の信頼性に尽きる：同じ座標を叩けば、いつでも「その単元・その形式・その難しさの、数学的に正しい問題」が無限バリエーションで返ること。

2.2 スコープ外（ホストの責務）

スコープ内（エンジン）スコープ外（ホスト側）
座標＋seed → 問題1件の生成／生成可能な座標の告知／正しさ・形式・難易度・図の保証 アダプティブ出題・習熟度モデル／出題順序・カリキュラム進行／採点UI・提出フロー／認証・課金・学習履歴

3. コアコンセプト：blueprint × atom（最重要・実装失敗の再発防止）

3.1 三要素の定義

要素定義現行実装
blueprint
（問題構造）		 「どんな部品スロットを持ち、部品に何をさせ、何を問うか」という問題の骨組み。部品の中身は知らない。 27種（BasicGeometryMeasurementStructure, PythagoreanStructure 等。apps/api/src/blueprints/registry.py）。スロットは noun_slots（タグで部品を募集）
atom
（部品・名詞）		 問題に登場する交換可能な素材（図形・数・式・データ等）。自分の性質（体積の求め方等）は自分が知っている。 21種（PrismAtom, PyramidAtom, SphereAtom, PolygonAtom, LinearFuncAtom 等。apps/api/src/atoms/noun/、タグ登録制）
verb
（操作）		 atom に対して行う数学的操作。SymPy で解き、答えと途中式（logic_steps）を確定する。ここが moat（正しさの堀）。 33種（MeasureGeometryVerb, TriangleAreaVerb, SolveSimilarityVerb, FactorizeVerb 等。apps/api/src/atoms/verb/）

3.2 拡張則（Open-Closed 原則）— このシステムの存在理由

拡張則（絶対要件） 生成できる問題は 「追加」だけで増えること。既存コードの「修正」を要してはならない。
atom を1つ追加すると、そのタグを受け入れるすべての blueprint の生成空間が同時に広がる（M×N の掛け算で増える）。blueprint を1つ追加すると、既存の atom 資産をそのまま使った新しい問題構造が生まれる。

例：空間図形の計量 blueprint

「立体を1つ選び、その体積・表面積を問う」という骨組み。スロットは「タグ=solid の atom」を募集するだけで、特定の立体名を知らない。

部品プール： 直方体 円柱 角錐 ＋ 立方体（新規追加）

→ 立方体 atom を追加した瞬間、この blueprint（および solid を使う他の全 blueprint）が立方体の問題を生成できるようになる。blueprint のコードは1行も変えない。

禁止パターン（過去の実装失敗の形）

  • blueprint 内に特定 atom 名の if 分岐を書く（部品を増やすたび blueprint の修正が要る＝拡張則違反）
  • 特定の数値・図形・題材のハードコード（seed を変えても同じ問題しか出ない）
  • form を無視して常に同じ生成物を返す（形式を選ぶ意味が消える）
  • LLM に答え・数値を生成/改変させる（moat 崩壊）

3.3 正しさの保証構造（moat）

問題の答え・数値・論理ステップ（logic_steps）は SymPy が決定論的に計算し、以後どの層も改変できない。LLM の役割は「確定した構造を自然な日本語に翻訳する」ことだけ（§4 L4）。これにより生成AIの不確かさが正しさに混入しない。世代①の失敗（難易度・図・正しさの不安定）の直接の対策である。

4. システム構成（4層と責務境界）

各層が「保証すること」を固定し、層をまたぐ責務の滲み出しを禁止する。現状の主要欠陥（計算問題にも図が付く／図に答えが書いてある）は境界規則の欠如が原因（§9）。

L0 ホスト教育システム（スコープ外）
生徒UI・出題戦略・採点フロー。エンジンに (unit, form, level, seed) を渡す
保証しない：問題の中身
▼ 座標＋seed
L1 入力層座標系＝input_spec
保証：座標（単元×形式7型×難易度段）が教育的に一貫し、相互排他で、生成可能な座標が問い合わせ可能
保証しない：生成の中身（L2以降）
▼
L2 構造層blueprint runner＋moat
保証：数学的正しさ（SymPy）・form の構造的忠実性・難易度の構造的分離・決定論（seed）
保証しない：自然な日本語・図の描画
▼ 中間表現（MR）＝構造＋答え確定済み
L3 図層visual DSL＋renderer
保証：form が図を要求するときだけ描く・答えを図に描かない・問題を解くのに必要な情報だけを持つ図
保証しない：問題文
▼
L4 言語層LLM翻訳
保証：MR に忠実な自然文（問題文・解説）。捏造・省略の検出ゲート付き
保証しない（禁止）：数値・答え・論理の改変

5.1 出力データ（Problem）の構造

Problem {
  content_problem_text : 問題文（LLM翻訳・答え非含有）

    label            : "(1)" …
    prompt_text      : 小問の問い
    answer           : { sympy_form, text_form, type }   ← SymPy確定値（moat）

  metadata : { blueprint_id, used_atoms, seed, difficulty, git_commit }

7. 品質要件（Q）＝1セルの「完成の定義」

座標セル (unit, form, level) が出荷可 ⇔ そのセルから生成される Problem が Q1〜Q6 をすべて満たす。これが従来欠けていた "done" の定義であり、以後の全修正はどの Q を改善するかを宣言して行う。

ID品質特性満たすべきこと検証手段
Q1正しさ（moat） 解答・数値・logic_steps が数学的に正しい。最優先・不可侵 決定論（SymPy 恒真・G4/G5/G6）
Q2形式忠実性 出た問題が本当に選んだ form である（計算セルに図付き文章題が出ない等） 決定論（form別の構造検査）
Q3難易度の分離 同一 (unit×form) 内で Lv を上げると構造が実際に変わり、易→難に単調 決定論（構造差分検査）＋LLM監査で意味確認
Q4題材忠実性 出た問題が選んだ単元の題材である（別単元の問題や固定パターンへの固着をしない） LLM監査（Opus・広く安く候補特定→絞って深く判定）
Q5答え非漏洩 問題文・図に答えが含まれない。図は解くのに必要な情報だけを持つ 決定論（G1 leakage＋図中文字列検査）
Q6自然さ 問題文・図が人間の教材として自然（通貨は円・離散量に分数を出さない・図のラベル衝突なし等） LLM監査＋人間サンプリング
検証コストの原則（確定済み方針） 数学的に検証できるもの（Q1/Q2/Q3構造/Q5）に LLM を浪費しない。LLM でしか測れない意味的品質（Q4/Q6）にだけ LLM を使い、全体評価（広く安く候補を特定）→個別評価（絞って深く判定）の二段で使う。

D-4 ホストAPIの具体形：capabilities のスキーマ・Problem スキーマの版管理（教育システム側の要求仕様） ホスト側の設計が見えた時点で確定（本書 v1.1 で追記）。それまで F-5 は内部スキャンツールとして先行実装
