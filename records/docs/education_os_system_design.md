## 0. なぜ立ち止まったのか（この文書が答える問い）

営業資料（サービス紹介・事業計画・経営計画）は、Education OS を **「塾運営を仕組み化する4層 OS」** として描いている。キーメッセージは「**先生の学力に頼らなくていい塾がつくれる**」「未経験でも標準品質」「AI が教材生成・採点・授業進行を担う」。

一方、教育論メモは、議論を重ねた末に別の言葉に到達している（メモ28章）:

> **モンジェネの存在理由 = 目撃しなくていい部分（採点・診断・道案内）を全部引き受け、人間の先生が "目撃だけ" に専念できるようにする装置。**

この2つは **矛盾していないが、同じではない**。営業資料を額面通りに実装すると「AI が全部やる塾」になりかねない。メモは「AI がやってはいけない一点（再着火・目撃）」を苦労して特定した。**この一点を設計に刻めるかどうかが、私たちのプロダクトが凡百の EdTech と分かれる境界線**である。

この文書は、メモの結論で営業資料を上書きし、そこから機能要件を逆算する。

---

## 1. 中心的な再定義：私たちが作るのは「目撃を最大化する装置」

**プロダクトの一言定義（改訂版）:**

> Education OS は、塾で起きる作業のうち **「目撃しなくてよい部分」を機械が全部引き受け、人間の先生が「一人の生徒の苦労を見続けること（目撃）」に専念できる状態を作る** システムである。

この定義から、あらゆる機能要件を判定する **単一の基準** が導ける:

> **その機能は、先生が生徒を「見る」時間を増やすか？ それとも「見なくてよく」してしまうか？**
>
> - 見る時間を増やす（採点・問題探し・進捗管理を肩代わり）→ 作る。
> - 見なくてよくしてしまう（生徒への声かけ・動機づけまで AI が代行）→ **作らない**。

メモ26章の警告を要件化したもの: 機械が作業を引き受けるほど「さばける人数（オペレーション上限）」は上がるが「深く見れる人数（目撃上限）」は上がらない。この乖離を無視して自動化を積むと **「高機能な放置塾」** に化ける。→ **自動化には意図的な上限がある（後述の設計原則 P6）。**

## 2. 資料間の「継ぎ目」を明示的に解消する

営業資料の3つの表現を、メモの結論で上書きする。**チーム内でこの3点の解釈を揃えることが、要件定義の前提。**

| 論点 | 営業資料の表現 | メモによる上書き（採用する解釈） | 根拠 |
|---|---|---|---|
| **① AI は教えるのか** | 「Layer 1 教材 AI が問題生成・採点」「学力依存を解消」 | **AI は教材（解説・インプットの中身）を作らない**。問題生成・採点・診断・「教科書のどこを読むか」の道案内までが AI の担当。概念の解説そのものは外部教材（学校・教科書）に外注する | メモ18〜20章「モンジェネは教材を作らない／道案内だけ」 |
| **② 先生の役割** | 「未経験でも標準品質」「先生の学力に頼らない」 | 先生は **教科を教えない**。だが役割は「監視員」ではなく、**最も難しい仕事（火つけ・伴走・帰属回収・再着火・目撃）を担う専門職**。学力不問採用は成立するが、対人スキルは高度に要求される | メモ20, 24, 27, 28章 |
| **③ 継続率はどう上がるのか** | 「コーチング OS が退塾リスクをスコアリングして継続率を標準化」 | **システムは退塾リスクを検知して先生に手渡すだけ**。継続を決める「再着火」は人間がやる。システムが再着火を代行してはならない（ゲーム・AI チャットは詰んだ子を追いかけられない = メモ24章） | メモ24, 28章 |

**結論**: Education OS の「4層」は正しい枠組みだが、各層で **「機械の担当」と「人間に残す担当」の境界線** を引き直す必要がある。それが本文書の残りの内容。

## 3. 設計原則（教育論メモから導出した8原則）

すべての機能はこの8原則に照らして設計・レビューする。原則名はメモの章番号に対応。

### P1. 非対称アシストの原則（メモ1章）
「正しい」は気前よく渡し、「間違い」は渡さない。
- **生徒に見せる採点結果と、先生に見せる診断は別物にする。**
  - 生徒向け: 「ここは合っている」「ミスはこの範囲に隠れている」まで。**どこがどう間違いか・正解は言わない。**
  - 先生向け: フルの診断（どのステップでどのエラー分類か、根本原因ノード、指導アクション）。
- ⚠️ 現行 ScoGene プロトタイプは「改善アドバイス」で **答えに近い情報を直接出している**。これは生徒に直接見せる用途では **P1 違反**。出力の宛先（生徒 / 先生）で見せ方を分離する要件が必須。

### P2. 帰属の設計（メモ4〜5章）
成功を「自分の力だ」と生徒本人に思わせる仕掛けを、システムが**先生に供給する**。
- 正解直後に「今、何をしたから解けたと思う？」を生徒本人に言わせる声かけを、先生向け画面に提示。
- 「正解えらい（結果）」ではなく「投げ出さずもう一回読んだね（過程）」を褒める材料を出す。→ ダッシュボードは正答率だけでなく **過程の粘り（再挑戦・見直し行動）** を可視化する。

### P3. クセ層の可視化（メモ2, 6章）
個別ミスの修理（点に直結）と、クセの修理（一生モノ）は別作業。
- エラー4分類（読解/変換/処理/書き写し）は **個別ミス層**。これに加えて、**時系列で反復するパターン（「確かめずに決めつける」「急ぐと符号を落とす」等のメタ認知的クセ）を検出する上位層**を持つ。
- 出力: 先生に「この子、前にも似た間違い方をしていないか？」の材料を渡し、**生徒本人の口で「自分がミスする時のパターン」を言語化させる**のを支援。

### P4. 足場の観測（メモ14章）※ v2 以降の設計含意
答案だけを読む診断は **「足場込みの偽の習得」を拾う**危険がある（Point/WarmUp を見ながら Try を解いた子は、正解し途中式もきれいだが独力ではない）。
- システムが与えた足場と、生徒が自給した足場を区別したい。
- 「見ないで書けるところまで書いて」の境界線を答案上に引かせる運用を、将来は一次情報として取り込む。
- **Phase 0 では現場運用（先生が目視）で対処。設計の頭の隅に置く。**

### P5. 再着火は人間に残す（メモ24, 28章）
着火・燃焼は機械が得意（むしろ AI の方が上手いことすらある）。**折れた後にもう一度机に戻る「再着火」だけが人間の領域。**
- システムは **退塾リスク・停滞を検知し、先生に「今この子に会って」と手渡す**。再着火の言葉・介入そのものは絶対に自動化しない。

### P6. 目撃を奪わない（自動化の上限）（メモ26章）
自動化は「先生が見る時間を増やす」ためにやる。「見なくてよくする」ためではない。
- 生徒への直接の声かけ・励まし・進路相談を AI で代替しない。
- 1校舎の適正実人数（先生が顔と苦労を思い浮かべられる人数）を、価格・スケール設計の土台とする（未確定・メモ26章の宿題）。

### P7. 選択麻痺を避ける（メモ9, 16, 22章）
「手が止まる」真犯人は、量への圧倒か、選択麻痺（どれからやるか選べない）。
- **生徒に提示する「次の一手」は常に1つ**。問題のメニューを並べない。苦手な子ほど選択肢は毒。

### P8. インプットは外注・道案内のみ（メモ18章）
教材（概念の解説）を自作しない。作り始めた瞬間、私たちは問題生成システムではなく**教材会社**になる（「SIer にならない」規律と同型）。
- インプットの中身 = 学校の授業・教科書に外注。モンジェネは知識グラフで「教科書のどこを読めばいいか」を指し示す（生成ゼロ・ナビゲーションのみ）。

## 4. スコープの線引き：私たちが「作らないもの」

原則から導かれる **非目標（Non-Goals）**。これを明文化することが、リソースを守り、放置塾化を防ぐ。

- ❌ 概念の解説コンテンツ・教材（映像/テキスト）の内製 → 外部教科書に外注（P8）
- ❌ 生徒への直接の励まし・声かけ・進路相談を行う AI チャット/アバター → 人間に残す（P5, P6）
- ❌ 生徒に「どこが間違いか・正解」を直接告げる採点 UI → 非対称原則（P1）
- ❌ 先生を不要にする「完全自動授業」 → 目撃の担い手を消してはいけない（P6）
- ❌ タブレット完結型（生徒が一人で黙々と進める）モデル → atama+/Qubena の土俵。私たちは「紙 + 人 + 塾内空間」（提案書3.1, メモ21章）

## 5. システム全体像：4層 × 3アクター

```
                     生徒          先生（コミュ特化）      塾長 / FC本部
                      │                  │                    │
 Layer 1 教材AI  ── 問題を解く ──── 採点結果を受け取り ──── （品質データ源）
   ・問題生成         （紙・撮影）      伴走の材料に使う
   ・自動採点/診断
   ・知識グラフ道案内
                      │                  │                    │
 Layer 2 授業OS  ── Point/WarmUp/Try ─ 授業進行の足場 ─────────
   ・授業進行支援       の流れに乗る      （非専門家でも回せる）
   ・先生向け伴走UI
                      │                  │                    │
 Layer 3 コーチOS ─ （継続する） ──── 退塾リスク通知を受け ──── 継続率を経営指標に
   ・退塾リスク検知                     再着火に動く（人間）
   ・目撃支援
                      │                  │                    │
 Layer 4 品質管理OS ───────────────── 授業品質データを供給 ── 採用/育成/FC標準化
   ・教室横断ダッシュボード
   ・FC 標準化
```

- **上の層ほど生徒に近く、下の層ほど経営を支える**（サービス紹介資料6ページの構造を踏襲）。
- mongene-v2（現行コード）は **Layer 1 の「問題生成」部分**。ScoGene は **Layer 1 の「採点」部分のプロトタイプ**。両者はまだ統合されていない。Layer 2〜4 は未着手。

## 6. 機能要件（レイヤー別・優先度付き）

優先度: **【最高】= Phase 0 MVP 必須 / 【高】= Phase 0 後半 / 【中】= Phase 1 実証で / 【低】= Phase 2 以降**

### Layer 1 — 教材 AI（問題生成 + 採点診断 + 道案内）

現行 mongene-v2 の資産を最大活用する層。**ここが最も出来上がっている。**

| ID | 要件 | 優先度 | 現状 | 原則 |
|---|---|---|---|---|
| L1-01 | 学習指導要領準拠の数学問題を無限生成（Atom/Blueprint/難易度制御・SymPy 検証・図形描画） | 【最高】 | ✅ ほぼ完成（177 lesson 4軸 100%） | — |
| L1-02 | 手書き答案を撮影 → LLM Vision で採点し、どのステップで間違えたかを特定、エラー4分類（読解/変換/処理/書き写し） | 【最高】 | 🟡 ScoGene プロト有（要統合） | P3 |
| L1-03 | **採点結果の2系統出力**: ①生徒向け（正誤 + 「合っている箇所」+ 捜索範囲の提示のみ）②先生向け（フル診断） | 【最高】 | ❌ 未分離（現状は答えに近い助言を直接出力） | **P1** |
| L1-04 | 苦手プロファイルの蓄積（概念ごとの習得確率を時系列で記録） | 【高】 | ❌ 未実装（BKT は MVP 外扱い） | — |
| L1-05 | 苦手プロファイルに基づく個別最適化生成（苦手克服モード） | 【高】 | 🟡 3パターン生成の基盤有 | P7 |
| L1-06 | **知識グラフ道案内**: つまずいた概念から前提ノードを遡り、「まず教科書の◯◯を読もう」と外部教材の該当箇所を指し示す（教材は生成しない） | 【高】 | 🟡 前提グラフ DAG 有（254 edges）。道案内 UI は未 | **P8** |
| L1-07 | **次の一手を常に1つだけ提示**（問題のメニューを並べない） | 【高】 | ❌ UX 要件未反映 | **P7** |
| L1-08 | クセ層の検出: 反復する間違い方のパターンを時系列で抽出し先生に提示 | 【中】 | ❌ 未実装 | **P3** |
| L1-09 | API コスト最適化（バッチ処理・キャッシュ・上限 ¥3,000/生徒/月） | 【中】 | 🟡 Prefetch 有。有料 Gemini 前提の見積り要 | 非機能 |

**採点エンジンで最重要なのは L1-03。** 現行 ScoGene の「改善アドバイス」は、そのまま生徒に見せると P1（非対称原則）に反する。同じ診断結果から、宛先別に2つの見せ方を生成する分岐が必須。

### Layer 2 — 授業 OS（未経験の先生が授業を回せる足場）

**「学力不問採用」を実際に成立させる層。ここが競争優位の実装本体。** メモ13章の Point/WarmUp/Try 構造を土台にする。

| ID | 要件 | 優先度 | 原則 |
|---|---|---|---|
| L2-01 | 授業進行ガイド: 各単元を Point（インプット）→ WarmUp（伴走）→ Try（独力）の3ステージで進める台本を先生に提示 | 【高】 | メモ13章 |
| L2-02 | **Point は「教科書のどこを開くか」を指すだけ**（先生は解説しない）。火つけの声かけ例を提示（「これができると何が見える？」） | 【高】 | P8, 20章 |
| L2-03 | WarmUp 支援: 途中式・計算結果を「生徒の口で言わせる」よう先生を促す（帰属設計の実装） | 【高】 | P2 |
| L2-04 | **Try で止まった時の原因分岐を先生に提示**: ①WarmUp が空洞（Point へ戻す）② 独力移行の正常な負荷（足場を一段足す）。答案のエラーが手順崩れか処理エラー止まりかで判定 | 【中】 | メモ13章, P4 |
| L2-05 | 「見ながら解く子」への声かけテンプレ（足場を奪わず本人の意思で一段下げさせる） | 【中】 | メモ15章, P4 |
| L2-06 | 翌週の小テスト（間隔反復）を自動スケジュール（FSRS）。「テスト＝勝てる場所」への書き換えを支援 | 【中】 | メモ5章 |
| L2-07 | 1対2〜1対複数で、誰にいつ寄り添うかの交通整理（Try 中に別の生徒へ切替） | 【低】 | メモ13章 |

**この層の設計難所（要件として明記）:** 教科を教えられない先生が、詰まった生徒の隣に座って「一緒に教科書を開く」ことを可能にする UI。先生に数学を教えさせず、かつ生徒を放置させない。**これが Education OS の一番難しい要件であり、一番の差別化。**

### Layer 3 — コーチング OS（継続率 = North Star KPI）

| ID | 要件 | 優先度 | 原則 |
|---|---|---|---|
| L3-01 | 退塾リスク・学習停滞のスコアリング（出席・進捗・答案の失速から検知） | 【中】 | メモ24章 |
| L3-02 | **リスク検知 → 先生に「今この子に会って」と手渡す**（再着火の起動は人間） | 【中】 | **P5** |
| L3-03 | **目撃支援ビュー**: 一人の生徒について「この1ヶ月どんな苦労をしたか（粘った瞬間・折れかけた瞬間）」を先生が思い出せる時系列。データではなく "目撃の再生" を助ける | 【中】 | メモ26章 |
| L3-04 | 同じ生徒を同じ先生が見続けられる担当固定の担保（1校舎1先生構造の支援） | 【低】 | メモ26章 |

**L3-03 が Layer 3 の魂。** 「学習時間120分」というデータではなく「その120分がどんな120分だったか」を先生が思い出す手がかりを出す。効く褒め = 目撃の蓄積（メモ26章）を、システムが**代行するのではなく増幅する**。

### Layer 4 — 品質管理 OS（塾長・FC 本部）

| ID | 要件 | 優先度 | 原則 |
|---|---|---|---|
| L4-01 | 教室横断の生徒・授業・収益ダッシュボード（経営データの一元管理） | 【低】 | 事業計画 |
| L4-02 | 継続率を教室・先生別に可視化（North Star KPI 85% の管理） | 【低】 | 経営計画 |
| L4-03 | 採用・育成の標準化（先生が替わっても品質が変わらない運用手順の配信） | 【低】 | 事業計画 |
| L4-04 | FC 展開のための標準オペレーション・パッケージ | 【低】 | Phase 3 |

## 7. 横断要件（全レイヤーに刺さる）

| ID | 要件 | 説明 |
|---|---|---|
| X-01 | **宛先別出力の一貫した分離** | あらゆる診断・分析は「生徒向け」「先生向け」「塾長向け」で情報粒度と語り口を変える。特に生徒向けは P1（非対称）を厳守 |
| X-02 | **紙のワークフローを壊さない** | 生徒は紙で解き、スマホ/タブレットで撮影。UI は紙前提（提案書2.1）。デジタル完結を強制しない |
| X-03 | **塾内完結による一次情報の収集** | 学習は塾の中で起きる（家ではない）。どのページで止まったか・先生を呼んだか等を全部観測できる設計（メモ21章）。プライバシー配慮とセット |
| X-04 | **FB への FB ループ** | 先生がシステムの診断に修正・補足を返せる。塾講師の経験知をシステムに還元する双方向ループ（提案書） |

## 8. 非機能要件

| 領域 | 要件 |
|---|---|
| コスト | API コスト上限 ¥3,000/生徒/月（経営計画リスク表）。Gemini Free Tier は 20 RPD で実用不可 → 有料プラン前提の原価計算が必要。バッチ・キャッシュで最適化 |

## 11. 未解決の論点（設計課題として引き継ぐ）

メモが「次に議論したい山」として残した問いは、そのまま **システム設計の未決定事項**。要件確定前に判断が要る。

1. **「手が止まる」真犯人（量への圧倒 vs 選択麻痺）** — 打ち手が正反対（メモ22章・最優先）。P7 の実装方針（次の一手をどう1つに絞るか）に直結。特に「教科書の前で固まる苦手な子」をどう支えるか（L2-02, L1-06 の詳細設計）。
2. **足場の自給を観測するか（P4）** — 「見ないで書けるところまで」の境界線を一次情報として取り込むか。取り込むと診断精度が上がるが UI 負荷が増す。Phase 1 で現場データを見て判断。
3. **目撃の上限 = 1校舎の適正実人数（メモ26章）** — 価格・スケール設計の土台。自動化をどこで止めるか（P6）の定量的な線引き。実証で計測する。
4. **「教科書で成立する子/しない子」の見分け（メモ19章）** — 独学スキルの低い苦手な子を、道案内だけで放置しないための分岐ロジック（L1-06 の詳細）。
5. **旗の言語化（メモ29〜30章）** — 「なぜ人がやることに意味があるのか」。これは効果ではなく信条。**プロダクトの Non-Goal（P5, P6）の根拠であり、機能で証明しようとしてはいけない**という設計上の戒めとして持つ。

## 12. 一枚まとめ

- **作るもの**: 目撃を最大化する装置。採点・診断・問題生成・道案内という「見なくてよい作業」を機械が全部引き受け、先生が「一人の生徒を見続けること」に専念できる状態を作る。
- **作らないもの**: 教材（解説）の内製 / 生徒への直接の動機づけ AI / 「どこが間違い・正解」を生徒に告げる採点 / 先生を消す完全自動授業。
- **最初の一手（Phase 0）**: 既に完成した問題生成（L1-01）に、採点統合（L1-02）と **宛先別 FB 分離（L1-03・非対称原則の具現化）** を足す。ここが凡百の EdTech と分かれる最初の分岐点。
- **一番難しく、一番の差別化（Layer 2）**: 教科を教えない先生が、生徒を放置せず隣に座れる授業 OS。学力不問採用を「放置塾」にしないための足場。
- **判定基準はいつも一つ**: 「その機能は、先生が生徒を見る時間を増やすか？ 見なくてよくしてしまうか？」
