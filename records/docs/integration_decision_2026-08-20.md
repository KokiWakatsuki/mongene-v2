## 0. ★最初に：受け口は「決める」ものではなく、**すでに本体に書かれていた**

charter は「モック側の受け口（関数シグネチャ or エンドポイント）を決める」と
書いているが、実際に `yukiwaria/mongene` を読むと**受け口は実装済み**だった。

| 本体側のファイル | 中身 |
|---|---|
| `services/api/app/providers/base.py` | `ProblemProvider` プロトコル。`PROBLEM_PROVIDER=seed\|engine` で差し替え |
| `services/api/app/providers/engine.py` | `WakatsukiEngineClient`。**`POST {ENGINE_BASE_URL}/v1/problems/generate`** を叩く |
| `services/api/app/providers/contract.py` | 契約の Pydantic モデル。**`extra="forbid"`** |
| `packages/shared/fixtures/problem-generation/{request,response}.json` | 受け入れ条件のフィクスチャ |
| `docs/specs/mvp/06-problem-generation.md` | 仕様の正 |

本体のコメントにこう書いてある——**「契約フィクスチャを満たした時点で
`PROBLEM_PROVIDER=engine` に切り替えるだけで接続完了になる。コード変更なし」**。

つまり作業4の実体は「どう繋ぐかを設計する」ことではなく、
**エンジンの応答を契約に合わせること**である。そして合っていない。
★この食い違いを測らずに「組み込み方を決めた」と書くと、繋ぐ日に全部出てくる。

## 1. 契約との差（全 630 セル × 1 seed を実測）

`extra="forbid"` と `hints: min_length=3, max_length=3` があるので、
**足りなければ型の検証で必ず落ちる**。「だいたい合う」では通らない。

| # | 論点 | エンジンの現状 | 契約の要求 | 差の大きさ（実測） |
|:--:|---|---|---|---|
| 1 | エンドポイント | `POST /generate` | `POST /v1/problems/generate` | 経路名だけ。**軽い** |
| 2 | 1回で何問 | 1問 | `count` 1〜10 | 束ねる層が要る。**軽い** |
| 3 | form の語彙 | 7種 | 5種 | ★`construction`/`find_value`/`graph_table` が契約に無い＝**110 セルが載らない** |
| 4 | hints | 小問ごとの**文字列** | **ちょうど3件**・`stage` 1..3・`role` | ★3件だったのは **12/629 問（1.9%）**。1件が573問・2件が44問。しかも stage と role が無い |
| 5 | answer の型 | `kind` = symbolic/choice/graph/proof | `type` = numeric/expression/proof/set/graph | ★`symbolic` 415個・`choice` 166個が**契約に無い**。写す規則が要る |
| 6 | 小問の問い | `prompt_text` | 必須の文字列 | ★**627/685 小問（91.5%）が空**。問いが `problem_text` に埋まっている |
| 7 | 図 | `visual_svg`（SVG 文字列） | `visuals.problem_diagram_url`（**URL**） | ★置き場が要る。エンジンは持たない |
| 8 | 難易度 | `level` 1〜5 | `level` ＋ `target_difficulty` 1〜100 | 対応表が要る |
| 9 | 識別子 | `problem_ref` | `schema_version`/`request_id`/`problem_key`/`lesson_id` | 詰め替えるだけ。**軽い** |
| 10 | 拒否の返し方 | HTTP **422** ＋ `code` | `errors[]` に `UNSUPPORTED_FORM` 等 | ★下の「再試行」を参照 |
| 11 | 個別最適化 | `purpose`/`cause_id` | `personalization`（習得度・誤答傾向・自己発見率）／`unlearned_lesson_ids` | エンジンは受け取らない。**無視して縮退できる**（契約に「null時は最適化なし」と明記あり） |

### 重いのは3つだけ（4・6・7）

10 項目のうち、**詰め替えで済むもの（1・2・8・9・11）と、作らなければならないもの
（4・6・7）と、判断が要るもの（3・5・10）**に分かれる。

- **④ hints が最大**。契約は3段（focus / strategy / last_step）を要求し、しかも本体側に
  `hint_check.py`（答えの混入を機械で検査）がある。エンジンは1問1文字列が9割。
  **これは詰め替えでは作れない。3段のヒントを生む仕掛けがエンジン側に要る。**
- **⑥ prompt_text の 91.5% 空**は、エンジンが「問題文に (1)(2) を書き込む」設計だから。
  本体は小問を別々に表示する前提なので、**どちらかが折れる**。
- **⑦ 図の URL 化**は置き場の話。SVG は中央値 3.8KB・最大 14.5KB と小さいので、
  data URI でも、Supabase Storage でも成立する（下の「図の渡し方」を参照）。

## 2. 実測値（この環境・2026-08-20）

### 起動（1回だけ払う）

| 段 | 実測 |
|---|--:|
| `import engine` | 193 ms |
| `bootstrap()`（recipe/solver/frame/ゲートの登録） | 162 ms |
| `load_curriculum()` | 255 ms |
| `load_family_dir()`（375枚） | 672 ms |
| **合計** | **1,282 ms** |

★**エンジンの README は「約 0.3 秒」と書いているが、実測は台帳だけで 927ms、
全部で 1.28 秒。** README を直すこと（Vercel のコールドスタートに直接効く数字なので、
楽観的な値が残っていると判断を誤る）。

### 生成（暖機後・中央値）

| 呼び方 | 中央値 |
|---|--:|
| ライブラリ直呼び（`bootstrap()` 済み・台帳を渡す） | **2.06 ms** |
| HTTP 経由（同じ30セル） | **3.5 ms** |
| ★HTTP にする税 | **約 1.4 ms** |

★★**台帳を渡さないと 1問 950ms かかる。** `engine.core.pipeline.generate()` は
`curriculum` / `families` を省略すると**毎回 375枚を読み直す**（memo が無い）。
ライブラリとして呼ぶなら、**呼ぶ側が台帳を1回読んで持ち回す義務がある**。
API はこれを `lifespan` でやっているから速い。

★もう1つの落とし穴: **`bootstrap()` を呼ばないと `Unsupported`（`frame 未登録`）が返る。**
例外ではなく「対応していません」という**正常な応答**で返るので、
気づかずに「このセルは生成できない」と読み違える。

### form 別（HTTP・中央値）

| form | 中央値 |
|---|--:|
| knowledge | 1.0 ms |
| find_value | 2.5 ms |
| construction | 2.8 ms |
| calculation | 3.1 ms |
| graph_table | 4.6 ms |
| word_problem | 4.7 ms |
| **proof** | **23.6 ms** |

### ★proof の裾（51セル × 3 seed = 153問）

| | |
|---|--:|
| 中央値 | 55 ms |
| p90 | 1,171 ms |
| p99 | 2,535 ms |
| 最大 | 3,324 ms |
| 500ms を超えた問題 | **30 / 153（19.6%）** |

最も遅い: `g2_l41.proof.Lv4`（3.3秒）・`g3_l49.proof.Lv3`（2.5秒）・
`g2_l48.proof.Lv2〜4`（1.4〜2.1秒）。
**同じセルを繰り返しても同じだけかかる**（前向き推論器の探索そのもののコスト。
暖機の問題ではない）。

★エンジンの README の「速さ」の表は calculation / find_value / word_problem /
graph_table の4つだけを載せていて、**proof を載せていない**。
いちばん遅いものが表から落ちているので、「実行時にその場で引ける」という結論が
表から導けなくなっている。**表に proof を足すこと。**

### 図と応答の大きさ

| | 中央値 | 最大 |
|---|--:|--:|
| SVG | 3.8 KB | 14.5 KB |
| 応答全体（JSON） | 1.7 KB | 16.9 KB |

### 再現性

同じ seed で2回叩いて**完全一致**（8セル・不一致0）。
別プロセス・別ハッシュ種でも一致することは既に押さえてある
（`check_reproducible.py`）。**seed を保存すれば同じ問題が戻る。**

## 3. 5論点への答え

### 論点1 — 呼び出し方 → **HTTP API**

**理由は速さではない**（税は 1.4ms しかない）。3つある。

1. **本体がもう HTTP で書いてある。** `WakatsukiEngineClient` が
   `POST {ENGINE_BASE_URL}/v1/problems/generate` を叩く形で実装済み。
   ライブラリにすると、動いているものを書き直すことになる。
2. **本体は Cloud Run（Python 3.13 / uv）、エンジンも Python。** 同じ言語なので
   ライブラリでも繋がるが、**台帳の持ち回りの義務が本体に移る**。
   上で測ったとおり、これを忘れると 1問 950ms（460倍）になり、しかも
   **落ちずに遅くなるだけ**なので気づきにくい。境界を HTTP にすると、
   この義務はエンジン側の `lifespan` に閉じる。
3. **エンジンの内部を出さない、という設計をエンジン自身が宣言している**
   （`app/main.py` の冒頭・README）。ライブラリにすると recipe やゲートが
   本体から見えてしまう。

★ただし**事前生成（3つめの選択肢）は捨てない**。論点2 を参照。

### 論点2 — 生成の時点 → **原則は実行時に引く。ただし proof は別扱い**

- **proof 以外（579セル）** は中央値 1〜5ms・最大でも 50ms 台。
  **実行時にその場で引く。** 事前生成は要らない。
- **proof（51セル）** は p99 が 2.5秒・最大 3.3秒。
  生徒が待つ経路（画面を開いて問題が出る）に 2.5秒を素で入れるのは無理がある。
  取れる手は3つ。**推奨は (b)。**
  - (a) そのまま実行時に引く — 実装ゼロ。ただし2割の proof で1秒以上待たせる
  - (b) ★**proof だけ先に作って持っておく**（seed のリストを持ち、必要時に引く）。
    再現性が保証されているので、**保存するのは seed だけでよい**。
    問題そのものを持たなくていいので、事前生成の欠点（在庫が古くなる）が出ない
  - (c) 非同期にして「準備中」を出す — 画面の作りに踏み込むので範囲外

★**この判断は「事前生成 vs 実行時」の二択ではない。** seed が再現するので、
「seed を事前に決めておいて、実物は実行時に引く」という中間が取れる。
**これがこのエンジンの再現性から出てくる、いちばん効く使い方。**

### 論点3 — 図の渡し方 → **SVG のまま渡す。URL 化は本体側で**

- SVG は中央値 3.8KB・最大 14.5KB。**画像に焼く理由が無い**（焼くと拡大でぼやけ、
  焼く処理の時間も乗る）。
- 契約は `problem_diagram_url` という **URL** を求めているが、
  **エンジンは置き場を持たない**（持つべきでもない。置き場は本体の関心）。
- 具体案: エンジンは `visual_svg` を返し続ける。**受け口（`WakatsukiEngineClient`）が
  SVG を Supabase Storage に置いて URL にする。** 本体には Storage がある
  （`services/api/app/storage.py`）。
- ★**契約に `visual_svg` を足すほうが素直かもしれない**（`extra="forbid"` なので
  勝手には入らない）。ただし契約は本体の仕様書（`06-problem-generation.md`）が正なので、
  **これはこちらの一存で決めない**。→ §5 の要判断へ。
- 本体側に `svg_sanitizer.py` が旧アーキテクチャの残骸として存在した
  （`_mongene-mvp.remnant-2026-08-20`）。SVG を直接渡す前提の作りが以前あった痕跡。

### 論点4 — 再現性 → **seed だけ保存すればよい（確認済み）**

同一 seed で完全一致（本文・小問・答え・解説・図・`problem_ref` まで）。
別プロセス・別ハッシュ種でも一致。

**保存するもの**: `(unit, form, level, seed)` の4つだけ。
**保存しなくていいもの**: 問題文・図・答え。

★ただし**ゲートに落ちる seed がある**。全 630 セルを `seed=11` で引いたら
1件が 422 になった（`g1_l2.calculation.Lv1` → `G-Q5t: 解答由来の値 '3' が
problem_text/hints に漏洩`）。**ゲートが正しく仕事をしている**（答えが問題文に
漏れた問題を出さない）。

拒否率を測った:

| セル | 50 seed 中の 422 |
|---|--:|
| `g1_l2.calculation.Lv1` | **6 個（12%）**（seed 11・15・24・31・40・42） |
| `g1_l23.calculation.Lv3` | 0 個 |

★**セルによって偏る。** 1 seed で全セルを引くと「630 中 1 件」に見えるので
軽く見えるが、**特定のセルでは 12% が落ちる**。
**呼ぶ側は「422 なら seed を変えて引き直す」を必ず持つ必要がある**
（`count` 件を返す約束をしているので、なおさら）。
契約の `errors[]` に落とすか受け口で再試行するかは実装の判断だが、
**再試行なしで `count` 件を約束すると、たまに足りない応答を返す**。

### 論点5 — 誤答分析 → **範囲外（charter どおり）**

エンジンは `cause_tags` を返すところまで。契約の `personalization` は
「null なら最適化なし」と本体側に明記があるので、**エンジンは受け取らずに縮退できる**。
`unlearned_lesson_ids` も同様。**繋ぐ日にこれで止まらない。**

## 4. 繋ぐ順番（軽いものから・落ちたら止まる形で）

```
① 経路と包み（1・2・9・11）  詰め替えだけ。/v1/problems/generate を足し、
                             count 件ぶん回して schema_version/request_id を返す
② answer の写す規則（5）      symbolic → expression / numeric、choice → set の
                             どちらに落ちるかを answer の中身で決める
③ form の対応（3）            construction/find_value/graph_table をどうするか（要判断・§5）
④ prompt_text（6）            小問の問いを分けて持つか、本体が問題文をそのまま出すか（要判断・§5）
⑤ hints 3段（4）              ★いちばん重い。作る仕掛けが要る
⑥ 図の URL 化（7）            受け口が Storage に置く
```

★**⑤ を先にやらないこと。** ①〜④ が終われば `count` と `errors[]` を含む形が
そろうので、**契約フィクスチャの request.json を投げて、response.json との差分を
機械で見られるようになる**。差分が見える状態を先に作ってから、いちばん重い ⑤ に入る。

## 5. ★一存で決めないこと（出題設計・仕様の正に触る）

| # | 論点 | なぜ判断が要るか |
|:--:|---|---|
| A | `construction` / `find_value` / `graph_table` の **110セル** | 契約の `problem_form` は5種。エンジンの3種を**契約に足す**のか、既存の5種に**寄せる**（例: find_value → calculation）のか。寄せると本体の画面の出し分けが変わる。仕様の正は `06-problem-generation.md` |
| B | 小問の問い（91.5% が空） | エンジンが「問題文に (1)(2) を書く」設計を変えるのか、本体が問題文をそのまま出すのか。**どちらも大きい**。engine 側を変えると golden 全件が動く |
| C | `visual_svg` を契約に足すか | 足せば置き場の話が消える。ただし契約は本体の仕様書が正 |
| D | hints 3段（focus / strategy / last_step） | エンジンに3段を生む仕掛けを作るのが本筋。ただし「段」の定義は**出題設計**（何を焦点と呼ぶか）。charter §5 の「やらないこと」に近い |
