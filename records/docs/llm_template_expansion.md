## 1. 現状：文章題はどう作られているか

文章題も LLM ゼロの完全決定論。実体は f-string である。

```python
# engine/packs/math/recipes/word_problem_linear.py:258 _scene_price_count
scenario = (
    f"1{counter}{price_a}円の{item_a}と1{counter}{price_b}円の{item_b}を"
    f"合わせて{total}{counter}買ったところ、代金の合計は{cost}円だった。"
)
```

- 数値は **answer-first**（答えを先に引いて場面の数値を逆算）＝割り切れない問題が原理的に出ない
- 品名・人名・地名は family YAML の候補リストから抽選（`item_candidates: [みかん|個, ...]`）
- 解説は solver の op 列 → 固定日本語辞書。ヒントはその解説から最後の1手を削ったもの

**変わるのは数値と固有名詞だけで、文の骨格は変わらない。**
1セルの組合せ数自体は大きい（g1_l25 Lv2 で約59万通り・40seed 重複ゼロを実測）が、
それは「同じ文型に別の数を入れた59万通り」であって文型は1つ。

場面の骨格＝`scenario_kind` は 2026-08-06 時点で **60個**（全部手書き）。

## 2. 現在のゲートが検証していないもの ★最重要

文章題の double-solve checker はこうなっている（`checkers/word_problem_quadratic.py:35`）:

```python
numbers = mr.params["numbers"]              # 場面文に出ている数値だけ
formulation, sol, values = solve_scene(kind, numbers, coeffs)
#             ↑ recipe が使ったのと同じ FORMULATION_BUILDERS[kind]
```

検証しているのは **数値 → 立式 → 解** の連鎖であって、
**日本語の場面文が本当にその数式を意味しているか**ではない。
G-GND も「given の数値が problem_text に出現するか」の照合だけ
（`core/verify/quality_gates.py:416`）。

したがって次はゲートを**全部通過する**:

| 日本語 | 数式 | 出る答え | 本当の答え |
|---|---|---|---|
| 横が縦より6cm**短い**長方形がある。その面積は55cm²である。縦の長さを x cm とする。縦の長さを求めよ。 | `x(x + 6) = 55`（本当は `x(x - 6) = 55`） | 5cm | **11cm** |

数式と解は完全に整合し、数値も本文に出ているため。

**x が何を指すかを本文が決めていないと、この欠陥は再現しない**（`x` を「横」と
読めば「短い」でも整合してしまう）。実物の `g3_l30.word_problem.Lv2` は
「縦の長さを x cm とする」「縦の長さを求めよ」を持っているので、
そこの「長い」を「短い」に変えると上の表になる。
これは人間が f-string を書いていたから顕在化しなかった穴で、
**LLM に書かせた瞬間に主要な故障モードになる。**

## 3. ルートA：場面の着せ替え（安全・推奨）

数式を据え置き、日本語の文脈だけを LLM に増産させる。

`a·x + b(k−x) = c` は果物の買い物でもバス代でも切手でも同一。
現状はここが 1:1 で溶接されている（`_SCENE_DRAWERS` と `FORMULATION_BUILDERS` が
同じ `scenario_kind` キー・`word_problem_linear.py:581`）。これを

```
scenario_kind（場面・LLM 増産可）  →  formulation_kind（数式・人間が管理）
        多                                    1
```

に分離すれば、数式に触れずに場面だけ N 倍にできる。
`formulate_*` は既存の検証済みコードなので G-Q1 の意味は保たれる。

LLM に書かせるのは:
- 場面の f-string（`scenario` / `quantities` / `ask_value`）
- 候補リスト（`item_candidates` 等）
- 各数値がどの物理量に対応するかの割り当て

意味ズレの余地は「単価と個数を取り違える」程度に限定される。

## 4. ルートB：新しい立式の型ごと増やす（要人間・増産にならない）

「動く点」「食塩水の濃度」「相似を使った影の長さ」のような新しい数学の型は、
`formulate_*` の新規作成・level_sep・dup_rate の分散設計・退化条件まで絡む。
LLM に下書きさせても人間のレビューがボトルネックになる。
現在の60個が手書きなのはこのコストのため。

## 5. 穴を塞ぐ：逆翻訳ゲート G-BT

ルートA を回すなら必須。

```
生成された日本語の文章題
   ↓ 別の LLM に「これを読んで方程式を立てよ」とだけ指示（答えも数式も見せない）
   ↓ sympy でパース
FORMULATION_BUILDERS が作った eq と srepr 一致するか
```

**recipe とは完全に独立した経路**である点が肝。
いまの checker が同じ builder を再利用していて塞げない穴を、ここだけが塞げる。

検証はオフラインで1回（scenario_kind ごと・数十seed）。
通ったら engine に焼き込み、**実行時は LLM ゼロのまま**。

> 対外的には「生成AIで作った問題を配信」ではなく
> 「**生成AIで作り、機械検証を通したものだけを凍結して配信**」と言える。
> 実行時の幻覚リスクはゼロのまま、文型の多様性だけ増える。

## 6. T2/T3（実行時 LLM）は別路線・後回し

`core/render/t1_template.py:219` で `tier != "T1"` は `NotImplementedError`。
T2/T3 は「生成のたびに LLM が言い回しを変える」路線で多様性は最大だが、
毎回コスト・毎回レイテンシ・毎回検証が要る。
ドリル用途ではルートA（オフラインで型を増やして凍結）のほうが費用対効果が高い。
