# 今後の計画（2026-08-14 立案）

エンジンの3つの面（図・日本語と数式・解説）を測って直し終えた時点で立てる。
前提となる実測はすべて `HANDOFF_engine_quality_2026-08-14e.md` にある。

---

## 0. 計画の背骨：**量産の前に、量産で増える欠陥を測れるようにする**

今日の実測がそう言っている。**新しく開けた3つの面すべてに実物の欠陥があった。**
しかも一番重いものは、どのゲートも通っていた。

```
g3_l37.find_value.Lv4
  問題文「三角形OABの面積を三角形PABの面積が2等分する」
  実際に解いているもの「△PAB = △OAB」（等積変形。2等分ではない）
  → 答え・解説・double-solve すべて正しい。日本語だけが違うことを言っていた
  → 7回のセッションを生き延びた
```

塞げなかった理由は構造で、**checker が recipe と同じ立式関数を呼び直している**から。
検証しているのは「数値 → 立式 → 解」の連鎖で、「**その日本語が本当にその数式を
意味しているか**」ではない（`llm_template_expansion.md` §2）。

**量産（計画5）は、この故障モードだけを増やす作業である。** 増えるのは場面＝日本語。
だから順序は動かせない。

## 2. 切り分けが「読み手コスト」を下げるという理屈

ここが計画の要。切り分けは**設計の美しさのためではなく、測る量を減らすため**にやる。

```
いま（1:1）
  場面を1つ足す → その場面専用の数式ができる → 逆翻訳を1回読む
  場面 N 個 → 読む回数 N 回

切り分けたあと（N:1）
  場面を1つ足す → 既に検証済みの数式を指す
  → 読むのは「場面の数量が、数式のどの記号に対応するか」の1点だけ
  → 数式そのものの正しさは既に double-solve が保証している
```

つまり切り分けると、**逆翻訳が確かめるべきものが「立式全体」から
「場面の数量 → 数式の記号の割り当て」に縮む**。ここだけなら機械で照合できる余地が出る
（場面が宣言した「この数はこの物理量」と、数式が期待する引数の対応を突き合わせる）。

**切り分けずに量産すると、逆翻訳を人が4,600回読むしかない。** だから順序は
「切り分け → 量産」で確定する。

## 3. 計画

### Phase A. 式と場面の切り分け（計画2）

**目的**: `scenario_kind`（多・増産可）→ `formulation_kind`（少・人が管理）に分ける。

1. **`formulation_kind` を場面から独立させる**
   `FORMULATION_BUILDERS` のキーを `scenario_kind` から `formulation_kind` に変える。
   family YAML の `scenario_set` に `formulation` を明示する（いまは名前が同じなので
   暗黙に一致している）。28個の対応表を1回書けば済む。
2. **場面が「数量の意味」を宣言する形にする**
   いまは f-string の中に暗黙。`{"unit_price": price_a, "count": total, ...}` のように
   **数量名で渡す**。数式側は数量名で受ける。取り違えがここで型になる。
3. **G-BT を「割り当ての照合」に縮める**
   場面が宣言した数量名と、数式が要求する数量名が一致するかを機械で見る。
   一致しない場面は焼き込まない。
4. 全走検証（テスト・7ゲート・逆翻訳・図）

**やらないこと**: 新しい数式を増やす（それは Phase D）。
**壊してはいけないもの**: answer-first（答えを先に引く）。ここを崩すと割り切れない
問題が出る。切り分けは場面の側だけを動かす。

**終わりの条件**: 場面を1つ足すのに数式を触らなくてよい、を実際に1件やって示す。

### Phase B. ループを量産に耐える速さにする

Phase A と並行してよい（独立）。**量産の前提条件**。

| 対象 | いま | やること |
|---|---|---|
| `engine.eval` | 35分・1コア | セル単位でプロセスに配る（約4倍） |
| golden 再承認 | 23分・1コア | 同上（`approve_all.py` に並列を入れる） |
| コーパス再生成 | 10分・1コア | 同上 |

根拠は今日の実測。`engine_tests` は `--no-cov -n 4 --dist worksteal` で
**2〜3時間 → 33分**になった。同じことを残り3つでやる。

**これをやらずに量産すると、1周が数時間になってループが回らなくなる。**

### Phase C. API 化（計画4-2）

**先に返すべき宿題が1つある**（今日 README に3か所書いた）:

> **生成した問題の保存先が `engine_core/` の中に無い。** 書き出しているのは
> `records/work/build_corpus.py`（本体の外）。`engine_core/` だけを移すと
> 生成はできるが結果がどこにも残らない。

1. **出力の受け皿を1つ決める**。候補は2つ。
   - 呼ぶ側が保存先を渡す（引数／環境変数）
   - エンジン側に `ProblemSink` のような抽象を1つ置き、実装は外
   後者を推す。API 化すると保存先は DB になる可能性が高く、そのとき
   「ファイルに書く」前提が残っていると作り直しになる。
2. **入口を絞る**。外に出すのは `generate` と `capabilities` の2つ。
   `spec_cli`（preview/check/approve）は開発用なので API に出さない。
3. **決定論を契約にする**。`seed` を外から必ず渡す。同じ入力で同じ問題が出ることを
   API のテストで押さえる（これが「無限生成」の信頼の根拠になる）。
4. 図は SVG 文字列で返す。ファイルに書かない（保存先を決めるのは呼ぶ側）。

### Phase D. 場面の量産（計画5）

**Phase A と B が終わってから。** 順序を守る理由は §0 と §2。

1. LLM に書かせるのは**場面だけ**（数式・解説・図には触らせない）
2. 書かせた場面は G-BT（割り当ての照合＋抜き取りの読み）を通ったものだけ焼き込む
3. 焼き込んだら `dup_rate` / `level_sep` / `answer_size` / `statement_size` を回す
   （場面が増えると重複率は下がるが、**問題文の大きさ**は増えやすい）
4. **数式を増やすのは人**。ルートB（新しい立式の型）は LLM に下書きさせても
   人のレビューが律速なので、量産の対象にしない

## 5. 順序が決まっている理由（まとめ）

```
A. 式と場面の切り分け ─┐
                       ├→ D. 量産
B. ループの並列化 ─────┘

C. API 化 は A/B と独立（並行してよい）。ただし「出力の受け皿」だけは A より先に決めると
   Phase A で場面を足すたびに保存先の話が再燃しなくてよい
```

- **A を先にやる理由**: 量産で増えるのは日本語＝場面。切り分けないと逆翻訳を
  人が4,600回読むことになる（§2）
- **B を先にやる理由**: 1周が数時間になるとループが止まる。今日の実測で
  eval 35分 + 承認 23分 + コーパス 10分 = 68分が1コアで直列
- **D を最後にやる理由**: 今日3面開けて3面すべてに欠陥があった。
  **測れないものを増やすと、増えた分だけ見えない欠陥が増える**
