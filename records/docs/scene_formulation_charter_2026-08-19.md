## 1. ゴールの状態（システムとして）

問題の「違い」に4つの段階がある。**段階ごとに、何が担保するかを決めた。**

| 段階 | 生徒にとっての意味 | 何が担保するか | いまの状態 |
|:--:|---|---|:--:|
| 1 | 数値が違う問題（**立式の練習**） | いまのエンジン（answer-first の抽選） | **できている** |
| 2 | 本質は同じだが、読んで初めて同じと分かる問題（**読解の練習**） | **場面の量産** | これから |
| 3 | まったく違う問題（考え方・途中式が変わる） | **式の量産**（＋対応する場面） | これから |
| 4 | 量産時に**人の確認をほぼゼロにする** | 検査の仕組み | 一部できている |

### 段階2の「本質は同じ」の線引き（ここが最重要）

**「りんごがみかんになる」「買い物が水そうになる」は段階2に入らない。**
狙うのは「ぱっと見では分からないが、立式してみたら同じだった」という水準。

```
1個130円のなしと1個110円のぶどうを合わせて10個買った。代金は1200円。
大人900円・子ども400円の入園料で、合わせて12人ぶん5300円払った。
50円切手と80円切手を合わせて20枚買って1300円だった。
```
→ 見た目は別物、式はどれも `ax + b(N − x) = T`。これが段階2。

### 段階4の到達点（正直な線）

**ゼロにはならない。** 日本語と式の対応を機械が確かめられるなら、いまの checker が
すでにそれをやれている（checker は同じ立式コードをもう一度通すだけなので、
日本語がどうであれ必ず一致する）。

**到達できる線は「新しい文型を初めて書いたときだけ、人が1回読む」。**
その1回で見つかった型が機械検査に1つ足され、以後は自動で捕まる。
同じ文型の量産（seed 違い・語彙違い）は**完全にゼロ**にできる。

これは今回の修正で実際に起きたことと同じ道筋である——「解説に交点と書いてある」
「頂点名に I が入る」「立体の図に寸法が無い」は、見つかった時点で走査になった。

## 3. 3層モデル（すり合わせ済み）

`records/work/_preview_engine_explainer.html` の図と、そのまま対応する。

| 説明図の箱 | 層 | 持つもの | 持たないもの |
|---|---|---|---|
| ① 設計図の「値段・個数・答えの引き方」「答えを先に引く」 | **Relation（関係）** | 数の引き方・非退化条件・答えの逆算 | **日本語を1文字も持たない** |
| ④ 文型「1個〇円の〇と…」 | **Scene（場面）** | 日本語・語彙・空欄の並び | **数を引かない・式の形を知らない** |
| ⑤ 式の型「〇x + 〇(〇 − x) = 〇」 | **Formulation（式）** | 代数だけ | 場面も語彙も知らない |

場面と式をつなぐのは**役割名**（`rate`＝1つあたり、`count`＝個数、`amount`＝合計、
`speed`・`time`・`ratio`）。場面は「役割にどの日本語を着せるか」だけを知っている。

### 式を増やすと場面も必ず要る、は**半分**

**役割の型が既存と同じなら、新しい式は既存の場面にそのまま乗る。**

```
ax + b(N − x) = T   （合わせて N 個）      役割 rate, rate, count, amount
ax + b(x + d) = T   （B は A より d 個多い） 役割 rate, rate, count, amount  ← 同じ
```
→ 買い物・入園料・切手・会費の場面を**共有できる**。

場面を新しく書く必要があるのは、**役割の型が新しいとき**だけ（速さ・時間など）。

## 4. 作業内容（確定）

### 作業0 — 物差しを直す（**切り離しより先**）

- **現状**: 型の数え方（`build_corpus`）は数値を伏せるが語彙は伏せない。
  語彙違いが型として数えられている（g2_l16.Lv2 = 49型／文型1）
- **作業**: 型を「文型（構成フラグ）」「語彙」「数」の3つに分けて数える。
  `count_patterns_wp.py` の判定（**鍵の名前でなく値の型で選ぶ**）を本体に入れる
- **ゴール**: g2_l16.Lv2 の型が 49 → 文型の数になる。以後、**場面を足したぶんだけ型が増える**

★この走査は一度外している。「surface らしい鍵の名前」を並べて除く書き方では
`item_a`（語彙）や `line_cost`（係数の並び）を取りこぼし、100セルすべてが
seed 数と同じ 30 型になった（＝走査が動いていない）。**値の型で選ぶ**こと。

### 作業1 — 構造を3層に割る（生成物は1文字も変えない）

- **現状**: `scenario_kind` が「数を引く＋日本語を書く」関数と「式を組む」関数を
  同時に引く。両者は `numbers` のキー名（`price_a`・`speed_go`）で縛られている
- **作業**: 役割名に統一 → 数の抽選を `Relation` へ → 残った日本語を `Scene` へ。
  対象は `word_problem_linear` → `system` → `proportion_frequency` → `quadratic` → `expression`
- **ゴール**（すべて機械で確かめる）
  - `approve_all.py` の差分**ゼロ**（構造だけが変わり生成物は同一）
  - eval 7ゲート OK / pytest 失敗 0 / ハッシュ種3通りで差分 0
  - **`Scene` のコードに `draw(` が1つも無い**
  - **`Relation` のコードに日本語が1文字も無い**

★最後の2つが「本当に切れたか」の唯一の判定。分けたつもりで Relation に日本語が
残るのがいちばん起きやすい。

### 作業2 — 検査の仕組みを作る（量産の前に）

- **現状**: checker は同じ立式コードを再実行するので、日本語と式の食い違いを
  **構造的に検出できない**。場面を増やすとここが唯一の穴になる
- **作業**: 機械化できるものと、人が1回読むものを分ける

| 検査 | 見るもの | 機械 / 人 |
|---|---|:--:|
| G-SC1 契約 | `scene.fits`・役割が全部埋まっているか | 機械（構成時） |
| G-SC2 数の出現 | 場面文に `numbers` が全部出ているか | 機械（既存テスト） |
| G-SC3 骨格 | 関係が要求する接続詞があるか（`合わせて` を要求し `ずつ` を禁じる） | 機械（新規） |
| G-SC4 単位・共起 | 助数詞と答えの単位／人に「いる」・物に「ある」／品物と助数詞が対 | 機械（新規） |
| G-SC5 場面の妥当性 | 引いた数が場面としてありうるか（速さ・人数・濃度の上下限） | 機械（新規） |
| **G-BT 逆翻訳** | **問題文だけ**を読んで式を立て、engine の式と突き合わせる | **人が1回**（新しい文型のみ） |

- **ゴール**
  - G-SC1〜5 が走査として動き、**合成データで「落ちる場合」も出る**（0件を出す検査は疑う）
  - G-BT が (関係×場面) 全組×5seed を出力でき、読み手に渡すのは**問題文だけ**
  - 新しい文型を1つ足したとき、人が読むのは**1回だけ**で済む

### 作業3 — 場面と式をいくつか作り、量産できるかを判断する

- **現状**: 文型 102・場面 53。1つの式に1つの場面が貼りついている
- **作業**: 場面を4つ（入園料・切手・会費・材料）、式を2つ足す。足すたびに実測を記録
- **ゴール（★「4つ作れた」は成功の証拠にならない）**

| 測る | 線 | 意味 |
|---|---|---|
| 場面1つに要した行数 | 80 行以下 | 日本語だけになっているか |
| 触ったファイル数 | **1**（`scenes.py` だけ） | 式・checker・テストに波及するなら切れていない |
| その場面が乗った関係の数 | 2 以上 | 掛け算になっているか |
| その単元の**文型**の数 | 増える | 語彙でなく文型が増えたか（作業0の物差しで） |
| dup_rate | 下がる | 軸が増えたことが出ているか |
| G-BT の食い違い | 0 | 日本語と式が対応しているか |

**触ったファイル数が1にならなければ、切り離しは未完成。作業1に戻る。**

### 作業4 — メインプロジェクトへの組み込み方を決める

- **現状**: 入口は `engine.core.pipeline.generate(GenerateRequest)`。モック本体は別リポジトリ
  `github.com/yukiwaria/mongene`。受け渡しはコーパスを HTML に焼く片方向だけ
- **作業**: 5つの論点に答えを出す
  - 呼び出し方（ライブラリ / HTTP API / 事前生成したデータ）
  - 生成の時点（実行時に毎回引く / 事前に作って選ぶ）
  - 図の渡し方（SVG 文字列のまま / 画像に焼く）
  - 再現性（**seed だけ保存すれば同じ問題が出ることは確認済み**）
  - 誤答分析は範囲外（エンジンの仕事ではない）
- **ゴール**: 5論点に選んだ答えと理由が書かれ、**1問あたりの生成時間の実測値**があり、
  モック側の受け口（関数シグネチャ or エンドポイント）が決まっている

### 作業5 — 量産する

- **現状**: 文型が1つしかない word_problem のセルが 98 / 100
- **作業**: 作業3で決めた手順を繰り返す
- **ゴール**
  - 文型が1つしかないセル **98 → 30 以下**
  - `dup_rate_max` の宣言を**外せる**セルが増える（表層でなく中身で通る）
  - G-BT の食い違い 0 / eval・golden・pytest 緑 / ハッシュ種3通りで差分 0

## 5. やらないこと（この作業の範囲外）

| やらないこと | 理由 |
|---|---|
| 問題数の配分（食塩水を8問に、など） | 出題設計であってエンジンの仕事ではない |
| 入試対策への証明セル追加 | 単元定義の話。判断が要る（`engine_open_items_2026-08-19.md`） |
| 誤答要因・前提関係の配線 | エンジンの役目は「単元・難易度・形式に対して適切な問題を出す」ことまで |
| 語彙を増やして型を稼ぐ | **段階2に入らない**。物差しを直したあとは数字にも出ない |

## 6. この作業で必ず守ること（過去に踏んだもの）

1. **作業1の「生成物が同一」を必ず通す。** 飛ばすと構造を変えたのか中身を変えたのかが
   分からなくなる。golden の差分だけがそれを教えてくれる
2. **増やした軸は `params` に載せる。** `dup_key` は params だけを見る
3. **定義域は狭めない。** dup が下がるのは軸が増えるからで、数を絞るからではない
4. **同じ規約を複数の場所に複製しない**（頂点名の `I` は4か所に散っていて、
   1か所直して作り直しても消えなかった）
5. **0件・過大な数を出す走査は、まず検査が動いているか確かめる**
   （作業0の走査は最初 100セルすべて 30 型を返した＝seed 数と同じ＝動いていない）
6. **図を足したら PNG に起こして見る。** ゲートは図の中身の誤りを検出しない
