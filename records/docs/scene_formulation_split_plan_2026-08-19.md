# 式と場面の切り離し — 計画（2026-08-19 版）

前の設計（`scene_formulation_split_design.md`・2026-08-17）から、外部評価への対応で
エンジンがかなり変わった。**変わった点を実測してから**計画を立て直す。

各タスクに **現状 / 作業内容 / ゴールの状態** を書く。ゴールは必ず**測れる形**で書く
（「きれいになる」ではなく「走査で N が 0 になる」）。

---

## 0. 前の設計から変わったこと（実測）

| 変わった点 | 前 | いま | 計画への影響 |
|---|---|---|---|
| 型の数え方 | narration の**数値を伏せていなかった** | 数値を伏せる（`build_corpus._mask_surface`） | **場面を足すと型が増える**が、数を替えただけでは増えない。切り離しの効果がそのまま数字に出る |
| dup の支え | 点名・使う文字の無作為さで閾を通していた | 表層を外し、**30セルに `dup_rate_max` を宣言** | 場面を足すことが dup を下げる**唯一の正しい手**になった |
| ヒント | 解説の手順の写し（93.6%） | **概念名から作る**（0.5%） | 場面文を変えてもヒントは動かない＝結合点が1つ減った |
| G-Q5t の数える語 | ゲートだけが持っていた | ゲートが唯一の出典・ヒント生成と共有 | 新しい場面が新しい助数詞を使うなら**ここに足す**（1か所） |
| level_sep | signature と fp の相異だけ | **(d) 最上位レベルの質的な差**を追加 | 場面を足しても Lv4 の差が消えないこと |
| 図 | 座標平面に軸名なし・立体に寸法なし | 軸名・寸法・場面図を配線済み | word_problem に図を足すときの部品が揃った |
| 再現性 | proof がハッシュ順に依存していた | 630セル×3seed×ハッシュ種3通りで差分0 | 切り離しで**壊れていないこと**を同じ道具で測れる |

### いまの結合の規模（実測）

```
word_problem の family 48 / セル 100 / コーパス上の問題 243
場面（_scene_* の登録数）  linear 8・system 7・pythagorean 10・probability 11
                          expression 5・proportion_frequency 4・quadratic 4
                          quadratic_function 4          … 合計 53
型が1つしかない word_problem のセル  85 / 100
```

**「型が1つしかないセルが85」が、この作業のいちばん大きな数字**である。場面が
式に貼りついているので、1つの式に1つの場面しか無い。ここが掛け算になる。

## タスク1 — 切り離しを完了する

### 1-A. 構造を3層に割る（生成物は1文字も変えない）

**現状**
`params["scenario_kind"]` が `_SCENE_DRAWERS`（数を引く＋日本語を書く）と
`FORMULATION_BUILDERS`（式を組む）を**同時に引く**。両者は `numbers` の**キー名**で
縛られていて、キーが場面の語（`price_a`・`speed_go`）になっている。

**作業内容**
1. `Formulation` の引数名を**役割名**に統一する（`price_a` → `rate_a`）。振る舞いは変えない
2. `_scene_*` から**数の抽選と非退化条件だけ**を抜いて `Relation.draw_numbers` に移す
3. 残った日本語を `Scene` にする（既存の場面＝各関係に1つ）。`SCENES` に登録
4. recipe は `relation` と `scene` を別々に引く

対象は `word_problem_linear.py` を先頭に、`system` → `proportion_frequency` →
`quadratic` → `expression` の順（`pythagorean`・`probability` は場面の性質が違うので後回し）。

**ゴールの状態**
- `approve_all.py` の差分が**ゼロ**（＝構造だけが変わり、生成物は同一）
- `python -m engine.eval` 7ゲート OK / `pytest` 失敗 0
- 630セル×3seed×ハッシュ種3通りで**差分 0**（`scratchpad/hashscan.py` と同じ手順）
- `Scene` のコードに**数を引く処理が1つも無い**こと（`draw(` を含まない）を機械で確かめる
- `Relation` のコードに**日本語が1文字も無い**こと（`[ぁ-んァ-ヶ一-龠]` を含まない）を機械で確かめる

★この2つの機械検査が、切り離しが本当にできたかどうかの**唯一の判定**である。
「分けたつもり」で日本語が Relation に残るのがいちばん起きやすい。

### 1-B. 品質チェックの仕組みを先に作る（量産の前に）

**現状**
`checker` は `FORMULATION_BUILDERS` を**もう一度通す**（`solve_scene` を共有）。
つまり**日本語がどうであれ double-solve は必ず一致する**。場面を増やすと、ここが
唯一の穴になる——新しい場面文が「合わせて12個」を「12個ずつ」と書き違えても、
どのゲートも落ちない。

**作業内容**
| 検査 | 何を見るか | いつ走るか |
|---|---|---|
| G-SC1 契約 | `scene.fits` に無い関係を着せたら例外／`relation.slot_types` を場面が全部埋めているか | 構成時（recipe の assert） |
| G-SC2 数の出現 | 場面文に `numbers` の値が全部出ているか | 既存 `test_recipes.py` が見る |
| G-SC3 単位 | `ask_value` の助数詞と答えの単位が一致 | 新規・全 (関係×場面) |
| G-SC4 語の共起 | 人・動物に「いる」／物に「ある」、品物と助数詞が対 | 新規・全 (関係×場面) |
| **G-BT 逆翻訳** | **問題文だけ**を読んで式を立て、engine の式と突き合わせる | (関係×場面) ごとに **5 seed** |

**ゴールの状態**
- G-SC1〜4 が `records/work/` の走査として動き、**合成データで「落ちる場合」も出る**ことを確認済み
  （0件を出す検査は、まず検査が動いているかを疑う）
- G-BT の手順が `records/work/bt_*.py` の延長として書かれ、**(関係×場面) 全組×5seed** を
  出力できる。読み手には**問題文だけ**を渡す（答え・解説・params を渡すと引きずられる）
- 既存の走査（`scan_b3.py`・`scan_hint.py`・`hashscan.py`）が切り離し後もそのまま通る

## タスク2 — 式と場面をいくつか作ってみる（量産できるかの判断）

**現状**
場面 53 に対し、式（関係）はほぼ同数。1対1で貼りついている。

**作業内容**
1. **場面を足す**: `two_kinds_total` に 4 つ（入園料・切手・会費・材料）
2. **式を足す**: 既存の場面に着られる関係を 2 つ（例 `three_kinds_total`・`remainder_split`）
3. 足すたびに `check_cell` で **dup_rate の実測値**を記録する
4. G-BT を新しい組だけ回す

**ゴールの状態（★ここが「量産できるか」の判断）**

| 測る | 合格の線 | 意味 |
|---|---|---|
| 場面1つ足すのにかかった行数 | **80 行以下** | 場面が「日本語だけ」になっていれば、この程度で書ける |
| 場面1つ足したときに触ったファイル数 | **1**（`scenes.py` だけ） | 式・checker・テストに波及するなら切り離せていない |
| その場面が乗った関係の数 | **2 以上** | 1 なら掛け算になっていない＝ただの場面追加 |
| 対象セルの dup_rate | 足す前より**下がる** | 軸が増えたことが数字に出ているか |
| G-BT の食い違い | **0** | 日本語と式が対応しているか |
| eval / pytest | 緑 | 既存を壊していないか |

**★「4つ作れた」は成功の証拠にならない。** 上の6つが揃って初めて量産できると言える。
とくに「触ったファイル数1」が満たせないなら、切り離しは未完成なので**タスク1に戻る**。

## タスク3 — メインプロジェクトへの組み込み方を決める

**現状**
- エンジンは `engine_core/` に閉じており、入口は `engine.core.pipeline.generate(GenerateRequest)`
- モック本体は別リポジトリ `github.com/yukiwaria/mongene`
- いまの受け渡しは、コーパスを HTML に焼く（`build_workbook_html.py`）片方向だけ

**作業内容（決めること）**
| 論点 | 選択肢 | 判断の材料 |
|---|---|---|
| 呼び出し方 | ① Python ライブラリとして import ② HTTP API ③ 事前生成したデータを配る | 生徒が単元・レベル・形式を選んで**その場で引く**なら①か②。①は同居が要る |
| 生成の時点 | 実行時に毎回引く / 事前に大量に作って選ぶ | 実行時は 1 問あたりの時間が要る（`check_cell` の実測で判断） |
| 図の渡し方 | SVG 文字列をそのまま / 画像に焼く | いまは SVG 文字列。Web ならそのままで良い |
| 再現性 | seed を保存するか、生成物を保存するか | **seed だけ保存すれば同じ問題が出る**ことは確認済み（ハッシュ種に依存しない） |
| 誤答分析 | 今回は範囲外（エンジンの仕事ではない） | 台帳の `error_causes` は未配線 |

**ゴールの状態**
- 上の5論点それぞれに**選んだ答えと理由**が書かれた設計メモがある
- 1問を生成するのにかかる時間を**実測**した数字がある（実行時に引くかの判断材料）
- モック側の受け口（関数シグネチャ or エンドポイント）が決まっている

## ★この計画で気をつけること（過去に踏んだもの）

1. **1-A の「生成物が同一」を必ず通す。** 飛ばすと、構造を変えたのか中身を変えたのかが
   分からなくなる。golden の差分だけがそれを教えてくれる
2. **増やした軸は `params` に載せる。** `dup_key` は `params` だけを見る。`scene` を
   params に入れないと、場面を5倍にしても dup は1ミリも下がらない
3. **定義域は狭めない。** dup が下がるのは軸が増えるからで、数を絞るからではない
4. **同じ規約を複数の場所に複製しない。** 頂点名から `I` を外す作業で4か所に散っていて、
   1か所直して作り直しても消えなかった
5. **0件を出す走査は、まず検査が動いているか確かめる**（修正を stash して同じ走査を回す）
6. **図を足したら PNG に起こして見る。** ゲートは図の中身の誤りを検出しない
