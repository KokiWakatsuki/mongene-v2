## ★★ 実際に踏まれた3つの失敗パターン

### 1. `variant_set` に op 列の違う variant を混ぜると G-FP が落ちる

**2体が同じ間違いをした。** 1レベル ＝ 1 signature ＝ **1 つの op 列**。

```yaml
# ダメな例（実際に g1_l51 Lv3 と g1_l52 Lv3 で起きた）
variant_set: [hemisphere_cylinder, cylinder_cone, reverse_cylinder_radius]
#             └─ 3手（重なりを除いて合成）──┘  └─ 2手（方程式化→解く）
```
→ seed によって fingerprint が変わり、`G-FP: fingerprint が不安定` で
120seed 中35〜65件が拒否される。

**対処**: 同じ op 列を持つ variant だけを1レベルに入れる。
op 列が違うものは別レベル（＝別 signature）に置くか、外す。

### 2. narration に数式の数字を書くと G-Q5t が誤検出する

```python
# ダメな例（g1_l53 Lv1・120seed 中114件が拒否された）
narration="球の表面積の公式（4πr²）に半径の値をあてはめて計算する。"
#                            ~~~~ この "²" が
```
答えの表示 `"36π cm²"` の **`cm²` から数値トークン `'2'` が抽出される**ため、
narration の `r²` と衝突して「解答由来の値が漏洩」と判定される。

**対処**: narration には数字を一切書かない。公式は言葉で述べる。
```python
narration="球の表面積の公式に半径の値をあてはめて計算する（半径の平方に比例する）。"
```

#### 2-a. `cm²` の右肩の `²` は本文の数値トークン `2` として読まれる（2026-08-07 実測）

```python
extract_numbers('面積が72cm²になる')  # -> ['72', '2']
```

つまり**面積を扱うセルで答えが 2 になる構成は、必ず G-Q5t で落ちる**。
構成の段階で外すこと（実行時に弾くのではなく、候補列挙から除く）。

#### 2-b. whitelist は `mr.given` 由来。`context_slots` の数値は許可されない

G-Q5t の whitelist は `mr.given` の値からしか作られない。誘導つき文章題で
**小問文を `context_slots`（`ask_value` など）に置くと、そこに出した数値は
whitelist に入らない**。「本文に出ているのに漏洩と判定される」のはこれ。

実例（g3_l38.word_problem Lv4）: 場面文（given.scenario）に 1辺と速さ、
問い（context_slots.ask_value）に面積を置いた。答えのグラフの折れ点
`(3s/v, 0)` の時刻が面積と一致する seed で落ちた。1辺・速さと一致しても
落ちないのは、そちらが given にあって whitelist に乗るから。

**対処**: 答えになりうる値の集合を構成時に洗い出し、`context_slots` に出す
数値と交わらないようにする。「本文に出ている数だから大丈夫」は成り立たない。

### 3. 定義域の広さを実測していない

「組合せは十分に広い」と source_desc に書いてあるのに、実際は 90〜130 通りしか
なかった、というのが3セルで起きた。

**dup_key = signature + params** なので、**params に入る値の組合せ数がすべて**。
context_slots（品名など）は dup_key に入らないので、いくら増やしても効かない。

**100seed で dup ≤ 0.20 を満たすには約 250 通り以上必要**
（誕生日問題: distinct = N(1-(1-1/N)^100)、N=250 で distinct≈80）。

| 組合せ数 N | 期待 dup |
|---|---|
| 90 | 0.42 |
| 130 | 0.35 |
| 200 | 0.24 |
| 250 | 0.20 |
| 350 | 0.14 |
| 660 | 0.06 |

**必ず定義域を数え上げてから YAML に書くこと。** 制約（`(360*r) % l == 0` のような
整除条件）があるなら、その制約を通った後の数を数えること。

### 4. check_cell が ALL_OK でも「台帳テスト」が赤になる（2026-08-07 に2件）

**check_cell はセル単位の生成ゲートしか見ない。** リポジトリ全体の不変条件を守る
テストは別にあり、pytest まで回さないと出てこない。実際に踏んだのは2種類:

- **frame の語彙台帳**（`engine_tests/unit/test_frames.py`）
  `frames.py` の `asked_vocab` に新しい動詞（`read_box_plot` など）を足したら、
  台帳テストの frozenset にも必ず足す。片側だけだと赤。
- **word_problem の params 忠実性契約**
  （`engine_tests/contract/test_word_problem_params_faithfulness.py`）
  word_problem のセルは `params["numbers"]` を**必ず持ち**、その値は**すべて本文に
  現れる数**でなければならない。図が数値を与えるセル（箱ひげ図など本文に算用数字が
  無いもの）は `"numbers": {}` と明示する。空にすると本文に算用数字が1つも無いことが
  併せて検査されるので、抜け道にはならない。例外リスト
  `_NO_NUMBERS_KEY_CELLS` に逃がさないこと。

**したがって DoD-2（pytest 全走）を飛ばして「check_cell が通ったので完成」と
報告してはいけない。** 実際、上限で落ちた1体はちょうどここで止まっていた。

## ★ 単一パラメータのセルは原理的に通らない

球の表面積のように **params が半径ひとつだけ**のセルは、半径を 2〜250 まで許さない限り
dup ≤ 0.20 に届かない。第2の軸（単位 cm/m/mm、半径で与えるか直径で与えるか、
立体の種類）を入れる**設計**が要る。目算で押し切らないこと。

その際、追加した軸が op 列を変えるなら G-FP に引っかかる（パターン1）。
「問題文から半径を読み取る」のような**variant 中立な第1手**を置いて op 列を揃える。

## その他の既知の罠（前回から継続）

- **params は「本文に出ている数値」だけ**。導出値を入れると検証に穴があく
- **level_sep は「何を文字に置くか」を動かす**のが一番効く
- **`sympy.nsimplify(文字列)` は偽の閉形式を返す**。solver に文字列係数を渡さない
- **draw した点ラベルは params に必ず含める**
- engine の検証は `--no-cov` 必須
- **worktree の基点を必ず確認**。`git log --oneline -1` が指示された基点と違ったら
  `git merge --ff-only <基点>` で揃えてから着手する
